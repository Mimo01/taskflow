# Phase 91.2: Code Review Report

**Reviewed:** 2026-08-13T00:40:00Z
**Depth:** standard
**Files Reviewed:** 8 (jira.ts limited to the phase diff vs `180b308d`: `PAGE_CONCURRENCY`, `fetchAllSearchPagesConcurrent`, `fetchEpicsBasic`, `fetchEpicEnrichmentMap`)
**Status:** issues_found

## Summary

The redesign is structurally sound: the div+flex row does keep exactly one `flex-1 min-w-0` cell, the fixed cells are all `flex-none` (no cell can collapse to zero width), the enrichment error-before-data read order is correct, and the fail-closed contract in `fetchAllSearchPagesConcurrent` is real (verified by test). Worker-pool ordering is also correct — `pages[i]` is indexed by offset slot, not completion order, and the shared `next++` index is safe under JS single-threading.

The defects are elsewhere. Two are stuck-UI blockers: the `isRefreshing` reset effect can never fire, so every "Retry" click on the error state or stale-data banner leaves the page showing a skeleton forever; and the enrichment query has no terminal state when it is disabled, so cached-but-token-less renders shimmer indefinitely with no error and no retry affordance. Beyond that: the concurrent pager trusts `PAGE_SIZE` instead of the server's actual `maxResults` (silent undercount — the exact failure mode its own doc comment says is unacceptable), it never aborts sibling pages after a failure, the enrichment query key omits the field-mapping settings it depends on, the `ORDER BY` flip mutates a cache key shared with three other surfaces, and the skeleton is wrapped in `p-4` while the settled rows are not — so every column shifts 16px when data lands, defeating the skeleton's stated purpose. Test coverage has matching holes: no test exercises the basic-query retry path, the column-order test asserts almost nothing its title claims, and the concurrency test cannot detect either unbounded parallelism or page reordering.

## Critical Issues

### CR-01: Retry leaves the page stuck on the skeleton forever

**File:** `taskflow/src/routes/dashboard/EpicsPage.tsx:208-212` (also `:239-242`, `:253-256`)
**Issue:** `showSkeleton = useDelayedLoading(isLoading) || isRefreshing`, and `isRefreshing` is only cleared by `useEffect(() => { if (!isLoading) setIsRefreshing(false); }, [isLoading])`. In react-query v5, `isLoading === isPending && isFetching`. Both retry buttons are only reachable when `isError` is true, i.e. `status === 'error'` — so `isPending` is already `false` and `isLoading` is already `false` *before* the click, and it stays `false` through the refetch and through success (`status` goes `error → success`, never `pending`). The effect's dependency array `[isLoading]` therefore never changes after the click, the effect never re-runs, and `isRefreshing` is never reset. Result: clicking "Retry" on `ErrorState` or `StaleDataBanner` replaces the page with `EpicsSkeleton` permanently — even after the refetch succeeds and data is in cache. The only recovery is a route change / remount. Not covered by any test in `EpicsPage.test.tsx`.
**Fix:** Drive the reset off fetch status instead of a stale-by-construction effect:
```tsx
const { data: epicsData, isLoading, isFetching, isError, error } = useQuery({...});
...
useEffect(() => {
  if (!isFetching) setIsRefreshing(false);
}, [isFetching]);
```
Better still, delete `isRefreshing` entirely and use `showSkeleton = useDelayedLoading(isLoading)`; `invalidateQueries` already re-renders through `isFetching`, and a full skeleton over already-cached rows is a downgrade from the stale-data banner anyway.

### CR-02: Disabled enrichment query renders an unrecoverable infinite shimmer

**File:** `taskflow/src/routes/dashboard/EpicsPage.tsx:179` and `:182-199`
**Issue:** `getEnrichmentState` has three outcomes: `error`, `ready`, and — as the fallthrough for "no data yet" — `pending`. There is no branch for "this query is disabled and will never run". The enrichment query is gated on `!!jiraBaseUrl && !!token && epicKeys.length > 0`, while epic rows can render from cache without a token: `readSecret('jira-pat')` failing (`.catch(() => setToken(null))`, line 131-134) leaves `token === null` forever, and the `['jira-epics-basic', activeJiraProject, jiraBaseUrl]` key is prefetched by `Sidebar.tsx:180-190` and served from the persisted query cache (`main.tsx` persister). In that state the basic query is disabled but `epicsData` is present, so `isLoading`/`isError` are both false and every row paints — with the Progress and Points cells locked in `kind: 'pending'` shimmer indefinitely. No error, no retry glyph, no timeout.
**Fix:** Make "disabled" a distinct terminal state rather than silently aliasing it to pending:
```tsx
const enrichmentEnabled = !!jiraBaseUrl && !!token && epicKeys.length > 0;
const { data: enrichmentMap, isError: enrichmentIsError, refetch } = useQuery({ ..., enabled: enrichmentEnabled });

function getEnrichmentState(epicKey: string): EnrichmentCellState {
  if (enrichmentIsError) return { kind: 'error' };
  if (enrichmentMap) { /* ...ready... */ }
  if (!enrichmentEnabled) return { kind: 'error' }; // retryable, not an endless shimmer
  return { kind: 'pending' };
}
```

## Warnings

### WR-01: Concurrent pager assumes the server honours `maxResults=200`; silently drops pages if it does not

**File:** `taskflow/src/services/jira.ts:344-404` (offset loop at `:383-384`)
**Issue:** Offsets are generated as `PAGE_SIZE, 2*PAGE_SIZE, …` while the response's own `maxResults` is never read. Jira DC/Cloud caps `maxResults` server-side (`jira.search.views.default.max`); if the cap is below 200, page 1 returns e.g. 100 issues and the next request starts at 200 — issues 100-199 (and 300-399, …) are never fetched and never noticed. The aggregate then reports understated `total`/`done`/`points` with a green "success" render. This is precisely the failure the function's own doc comment declares unacceptable ("a silently short result is worse than a visible error"), yet fail-closed only covers HTTP failure, not short pages. The sequential helper shares the flaw, but it at least stops on `issues.length === 0`; the concurrent version has no such guard at all.
**Fix:** Derive the step from the server's answer and fail closed on inconsistency:
```ts
const first = await fetchPage(0);
const step: number = first.maxResults ?? PAGE_SIZE;
if (step <= 0) throw new Error('Jira returned maxResults=0');
for (let startAt = step; startAt < total; startAt += step) offsets.push(startAt);
```

### WR-02: No cancellation after the first page failure — the pool keeps hammering Jira

**File:** `taskflow/src/services/jira.ts:392-401`
**Issue:** When a page rejects, only that worker unwinds. `Promise.all` rejects immediately, but the other 5 workers keep pulling from `next` and keep issuing requests for every remaining offset; nothing observes their results. On a 50-page enrichment during a Jira outage that is ~45 wasted requests per attempt, multiplied by react-query's retry count and by the user-facing retry glyph. The `if (page)` guard at line 403 is also dead under the fail-closed contract and would silently swallow a hole if that contract ever regressed.
**Fix:** Share a failure flag (or an `AbortController` threaded into `apiFetch`) and check it at the top of the worker loop:
```ts
let failed = false;
const workers = Array.from({ length: n }, async () => {
  while (!failed) {
    const i = next++;
    if (i >= offsets.length) return;
    try { pages[i] = (await fetchPage(offsets[i])).issues ?? []; }
    catch (e) { failed = true; throw e; }
  }
});
```
And replace `if (page)` with an explicit `if (!page) throw new Error(...)` so a hole can never be silent.

### WR-03: Enrichment query key omits the field keys the query function depends on

**File:** `taskflow/src/routes/dashboard/EpicsPage.tsx:170-178`
**Issue:** `queryFn` closes over `storyPointsFieldKey` and `epicLinkFieldKey` from the settings store, but the key is `['jira-epics-enrichment', activeJiraProject, jiraBaseUrl, epicKeys.join(',')]`. Changing the story-points or epic-link field mapping in settings produces a cache hit on the old entry — the page keeps showing counts computed with the wrong custom field until the cache expires. Same class of bug for the basic query at line 147 with `epicNameFieldKey`/`epicColorFieldKey` (pre-existing, but re-committed here).
**Fix:** `queryKey: ['jira-epics-enrichment', activeJiraProject, jiraBaseUrl, epicKeys.join(','), storyPointsFieldKey, epicLinkFieldKey]`.

### WR-04: `ORDER BY` flip silently reorders three other surfaces sharing the same cache key

**File:** `taskflow/src/services/jira.ts:2507-2509`
**Issue:** `fetchEpicsBasic` changed from `ORDER BY updated DESC` to `ORDER BY created ASC`, and its result is cached under `['jira-epics-basic', activeJiraProject, jiraBaseUrl]` — a key also written/read by `Sidebar.tsx:163-190`, `BacklogPage.tsx:514`, and `SprintBoardTab.tsx:991`. Those surfaces' epic pickers/filters now list epics oldest-first with no phase decision covering them and no test asserting either ordering. The change is intended for /epics only; it leaked.
**Fix:** Either add an explicit `orderBy` parameter (`fetchEpicsBasic(..., orderBy: 'created ASC' | 'updated DESC' = 'updated DESC')`) with distinct cache keys per ordering, or sort client-side in `EpicsPage` and leave the shared fetcher's JQL alone. If the global reorder is intended, add assertions in the Backlog/SprintBoard tests recording it.

### WR-05: Skeleton is inset by `p-4` while settled rows are not — every column reflows on load

**File:** `taskflow/src/routes/dashboard/EpicsPage.tsx:262-265` vs `:269`
**Issue:** `EpicsSkeleton` renders inside `<div className="p-4">`, but the real rows render inside `<div className="w-full text-sm">` with no horizontal padding. Every skeleton column is therefore shifted 16px right and the flex-1 name column is 32px narrower than the settled row. `EpicsSkeleton.tsx:4-8` claims "mirrors EpicRow's settled cell widths exactly so nothing reflows when real data lands" — it does the opposite. Secondary mismatch: the skeleton's priority placeholder is `h-3.5 w-3.5` (14px) inside a cell with no width, while `EpicRow` reserves a fixed 18px box (`EpicsPage.tsx:64-66`), so that column shifts a further 4px.
**Fix:** Drop the `p-4` wrapper (`{showSkeleton ? <EpicsSkeleton /> : …}`) and size the skeleton's priority placeholder to the same 18px box the row reserves.

### WR-06: Progress cell is too narrow for its own contents at 3-digit counts

**File:** `taskflow/src/routes/dashboard/EpicsPage.tsx:97` / `EpicProgressCells.tsx:75-100`
**Issue:** The cell is `flex-none w-32 px-2` → 112px of content box. Contents are a fixed `w-16` (64px) bar + `gap-1.5` (6px) + a `whitespace-nowrap` label. That leaves 42px for the label; `123/456` at `text-xs tabular-nums` is roughly 46-50px. Since the cell is `flex-none` (cannot grow) and the label cannot wrap or truncate, the overflow paints over the Points column. Epics with 100+ stories are ordinary.
**Fix:** Widen to `w-36`/`w-40`, or shrink the bar to `w-12` and let the label own the remainder. Add a rendering test with `total: 456, done: 123`.

### WR-07: Assignee cell reserves 16px of content box for a 24px non-shrinkable avatar

**File:** `taskflow/src/routes/dashboard/EpicsPage.tsx:107-113` (and `EpicsSkeleton.tsx:48-50`)
**Issue:** `flex-none w-10` = 40px total, minus `pl-2 pr-4` = 24px padding → 16px content box, while `CachedAvatar size={24}` renders a `shrink-0 size-6` (24px) box. The avatar overflows its content box by 8px into the right padding, so the effective right gutter is 8px, not the intended 16px — and the row's rightmost element sits closer to the container edge than the `px-6` page header. The skeleton repeats the same geometry, so it is consistently wrong rather than correct. This is the "fixed-px sizing in a flex row" trap from prior phases.
**Fix:** `flex-none w-14 pl-2 pr-4` (24px content + 24px padding = 56px) so the avatar occupies its declared box.

### WR-08: Duplicate structurally-coupled count types with no link between them

**File:** `taskflow/src/routes/dashboard/EpicProgressCells.tsx:20-27` vs `taskflow/src/services/jira.ts:2527-2534`
**Issue:** `EpicProgressCounts` and `EpicEnrichmentCounts` declare the same six fields independently. `EpicsPage.tsx:187` feeds the service type straight into the component type; TypeScript accepts it structurally, so a rename or semantic change on one side (e.g. `donePoints` → `completedPoints`) compiles fine at the boundary only until it does not, and the failure surfaces far from the change. Two sources of truth for one shape.
**Fix:** `import type { EpicEnrichmentCounts } from '@/services/jira'` in `EpicProgressCells.tsx` and `export type EpicProgressCounts = EpicEnrichmentCounts;` (or drop the alias entirely).

### WR-09: `fetchEpicsWithEnrichment` is now dead production code carrying drifted duplicate logic

**File:** `taskflow/src/services/jira.ts:2596-2677`
**Issue:** Grep shows the only remaining references are in `jira.test.ts`. It duplicates the aggregation loop that was just upgraded in `fetchEpicEnrichmentMap` but retains the old shape (`{total, done, points}` — no `inProgress`, no `donePoints`), the old `ORDER BY updated DESC`, and the old error-swallowing `.catch(() => [])`. This phase deleted the `services/jira/epics.ts` duplicate for exactly this reason; this one was left behind, so the codebase still has two divergent epic aggregators.
**Fix:** Delete `fetchEpicsWithEnrichment` and its test block (`jira.test.ts:1325-1478`), or, if a caller is planned, rewrite it as `fetchEpicsBasic` + `fetchEpicEnrichmentMap`.

### WR-10: Banner-reset effect does nothing its comment claims

**File:** `taskflow/src/routes/dashboard/EpicsPage.tsx:214-217`
**Issue:** `// Reset banner dismissal when error state changes` above `useEffect(() => { setBannerDismissed(false); }, [])` — an empty dependency array means it runs once on mount and never again. Once a user dismisses the stale-data banner, no subsequent failure will ever re-show it for the lifetime of the mounted page, so later stale data is presented as fresh with no indication. Pre-existing, but carried forward into a rewritten file with a comment asserting behaviour that does not exist.
**Fix:** `useEffect(() => { setBannerDismissed(false); }, [isError]);` — or delete the effect and the misleading comment if once-on-mount is genuinely intended.

### WR-11: `EPIC-02` column-order test does not test column order

**File:** `taskflow/src/routes/dashboard/EpicsPage.test.tsx:104-119`
**Issue:** The test is named "renders row columns in order key, name, status, priority, progress, points, assignee" — which is not even the implemented order (`EpicsPage.tsx` renders key, **priority**, name, status, progress, points, assignee). Its assertions only check that key precedes name and that the row has 7 children. Swapping status with points, or moving priority to the end, passes. The one D-05/D-10 layout decision under test is effectively unguarded, and the misleading title will send a future reader to the wrong conclusion about intended order.
**Fix:** Assert the actual sequence, e.g. map `Array.from(row.children)` to a stable per-cell `data-testid` (`data-testid="epic-cell-key" | "epic-cell-priority" | …`) and `expect(ids).toEqual([...])`. Rename the test to the implemented order.

### WR-12: Concurrency test cannot detect unbounded parallelism or page reordering

**File:** `taskflow/src/services/jira.test.ts:1621-1648`
**Issue:** Two things the new helper exists to guarantee are untested. (a) `maxInFlight).toBeGreaterThan(1)` — with only 3 pages (2 offsets) the pool spawns `min(6, 2) = 2` workers, so the assertion passes identically whether `PAGE_CONCURRENCY` is 6, 60, or removed entirely. (b) The test asserts only `total`, an order-insensitive sum, so the `pages[i]` slot-indexing (the entire reason for the `next++`/`pages[]` design over `push`) would survive being replaced with completion-order `push` without a single failure.
**Fix:** Use ≥ 10 pages with a jittered per-page delay, assert `maxInFlight <= 6` (export `PAGE_CONCURRENCY` or assert the literal), and assert issue-key order across the flattened result matches ascending `startAt`.

### WR-13: Unscoped `invalidateQueries` blows away every project's epic cache

**File:** `taskflow/src/routes/dashboard/EpicsPage.tsx:242` and `:255`
**Issue:** `queryClient.invalidateQueries({ queryKey: ['jira-epics-basic'] })` prefix-matches, so retrying on one project invalidates the cached epic list for every project and base URL, including the Sidebar's prefetched entries for other routes. Refetch-on-mount then re-issues those queries.
**Fix:** `queryClient.invalidateQueries({ queryKey: ['jira-epics-basic', activeJiraProject, jiraBaseUrl] })`.

### WR-14: Retry glyph gives no in-flight feedback and cannot be debounced

**File:** `taskflow/src/routes/dashboard/EpicsPage.tsx:204-206` / `EpicProgressCells.tsx:50-66`
**Issue:** `handleRetryEnrichment` calls `refetchEnrichment()` and discards the returned promise; `enrichmentIsError` stays true for the whole refetch, so the UI is byte-identical before, during, and after a failed retry. Every row shows two retry buttons, all wired to the same whole-batch query, and nothing disables them while a fetch is in flight — a user seeing "nothing happened" will click repeatedly, and each click re-issues an up-to-N-page concurrent batch (see WR-02 for the amplification).
**Fix:** Surface `isFetching` from the enrichment query, pass it into the cells, and render the pending shimmer (or a disabled/spinning glyph) while a retry is in flight:
```tsx
if (enrichmentIsError) return enrichmentIsFetching ? { kind: 'pending' } : { kind: 'error' };
```

## Info

### IN-01: `cn()` wrapping a single static string literal

**File:** `taskflow/src/routes/dashboard/EpicProgressCells.tsx:34-36`
**Issue:** `const RETRY_BUTTON_CLASS = cn('inline-flex …')` — `cn` merges/dedupes conditional class lists; with one literal argument it is pure overhead and implies conditional logic that is not there.
**Fix:** Drop the `cn()` wrapper and the import if unused elsewhere in the file.

### IN-02: `useMemo` for `epicKeys` never memoizes

**File:** `taskflow/src/routes/dashboard/EpicsPage.tsx:158-163`
**Issue:** `const epics = epicsData ?? []` allocates a fresh array on every render whenever `epicsData` is undefined, so `useMemo(..., [epics])` recomputes each time. Harmless (the query key uses the joined string) but the memo signals a stability guarantee it does not provide.
**Fix:** `const epicKeys = useMemo(() => (epicsData ?? []).map(e => e.key), [epicsData]);`

### IN-03: Floating-point story-point totals render unrounded

**File:** `taskflow/src/services/jira.ts:2583` / `EpicProgressCells.tsx:136`
**Issue:** `entry.points += sp` accumulates raw numbers; Jira allows fractional estimates (0.1, 0.3), so `donePoints`/`points` can render as `8.100000000000001/20 SP`.
**Fix:** Round at the render boundary: `{Math.round(counts.donePoints * 100) / 100}/{Math.round(counts.points * 100) / 100} SP`.

### IN-04: Two identical retry controls per row

**File:** `taskflow/src/routes/dashboard/EpicsPage.tsx:98` and `:103`
**Issue:** On enrichment failure each row exposes both "Retry loading epic progress" and "Retry loading epic story points", which trigger the exact same whole-batch refetch. For 30 epics that is 60 tab stops to the same action, and the distinct aria-labels imply a per-cell scope that does not exist.
**Fix:** Render the retry affordance in the progress cell only and show a static `—` in the points cell on error, or relabel both to "Retry loading epic progress and points".

### IN-05: Percentage segment widths can leave sub-pixel muted slivers

**File:** `taskflow/src/routes/dashboard/EpicProgressCells.tsx:81-96`
**Issue:** Three percentage widths summing to 100% over a 64px bar round independently, so `bg-muted` can show through as a hairline (most visible at `total` values like 3 or 7 with a fully-done epic, where the bar should read as solid green).
**Fix:** Give the last non-zero segment `flex-1` instead of a percentage width so it absorbs the rounding remainder.
