## Summary

This phase redesigns `/epics` from a 5-column `<table>` into a data-dense one-line-per-row portfolio view. All required primitives (`PriorityIcon`, `statusPillClass`, `CachedAvatar`, `epicColorToTailwind`, `useDelayedLoading`, `EmptyState`/`ErrorState`/`StaleDataBanner`) already exist and are already used on this exact page or its closest sibling (`BacklogRow.tsx`). No new npm packages, no new shadcn blocks, no new API calls — everything is a client-side reshape of two existing fetchers plus a new small segmented-bar component.

**The single most important finding is a file-resolution trap that directly contradicts `91.2-CONTEXT.md`'s canonical file list.** `src/services/jira/epics.ts` — the file CONTEXT.md names as the fetcher to edit — is **dead code**. Nothing imports from it outside its own colocated test. `EpicsPage.tsx` imports `fetchEpicsBasic`/`EpicEnriched` from `@/services/jira`, and because both `src/services/jira.ts` (a 2,600+ LOC file) and `src/services/jira/index.ts` (a barrel) exist, the bare specifier `@/services/jira` resolves to the **file**, `src/services/jira.ts`, not the directory index (confirmed: `src/services/jira/index.ts` only re-exports `attachments`, `duration`, `types`, `users`, `worklogs` — it does not re-export `epics`; `EpicsPage.test.tsx` mocks `vi.mock('@/services/jira', ...)` and that mock is what the component actually consumes). `fetchEpicsBasic`, `fetchEpicEnrichmentMap`, `fetchEpicsWithEnrichment`, and `fetchEpicStories` are duplicated byte-for-byte(ish) inside `src/services/jira.ts` at lines ~2410–2600. **All code changes for this phase belong in `src/services/jira.ts`, not `src/services/jira/epics.ts`.** This matches the project's documented "jira.ts dual-file gotcha" pattern.

**Primary recommendation:** Edit `src/services/jira.ts`'s epic section (ORDER BY, priority field, per-status-category enrichment counts, `donePoints`, remove the error-swallowing `.catch`), leave `src/services/jira/epics.ts` untouched (or delete it in a follow-up — out of scope here, flag as a note), rebuild `EpicRow` using the `BacklogRow.tsx` div+flex-row idiom instead of `<table>`/`<td>`, and wire a second `useQuery` for enrichment exactly the way `BacklogPage.tsx` wires its `epicNames`/`epicColors` maps — non-blocking, merged by key, never reordering the first-paint list.

### Pattern 1: Table → div+flex row conversion (project-standard fix for zero-width columns)
**What:** Replace `<table>`/`<colgroup>`/`<td>` with a `<div className="flex w-full items-center ...">` row containing `flex-none` cells with explicit widths and one `flex-1 min-w-0` cell for the variable-width content (epic name here — analogous to `BacklogRow`'s `summary` cell).
**When to use:** Any row where narrow fixed-width columns (icon, key, priority, points) sit alongside a growing text column, in the Tauri/WebKit webview — table layout's automatic column sizing has repeatedly collapsed narrow columns to 0px in this codebase (documented recurring bug, e.g. `CachedAvatar`, sprint board).
**Example (adapted from `BacklogRow.tsx`):**
```tsx
// Source: taskflow/src/routes/dashboard/BacklogRow.tsx (lines 90-213), this codebase
<div className="flex w-full items-center border-b border-border hover:bg-muted/30 cursor-pointer">
  {/* 1px colour bar — flex-none, explicit width */}
  <div className="flex-none w-1 self-stretch" style={{ backgroundColor: ... }} />

  {/* Key — flex-none, fixed width, mono */}
  <div className="flex-none w-24 px-2 py-2 density-compact:py-1 density-comfortable:py-3">
    <span className="font-mono text-xs text-muted-foreground">{epic.key}</span>
  </div>

  {/* Name — flex-1 min-w-0 so it truncates instead of collapsing siblings */}
  <div className="flex-1 min-w-0 px-2 py-2 density-compact:py-1 density-comfortable:py-3 overflow-hidden">
    <span className="truncate ...">{epic.epicName}</span>
  </div>

  {/* Status, priority, progress, points, assignee — all flex-none, explicit widths */}
  ...
</div>
```

### Pattern 2: Progressive enrichment behind a fast basic query (house pattern)
**What:** A second `useQuery` keyed off the already-loaded basic list's keys, `enabled` only once those keys exist, whose result is a `Map<key, enrichment>` merged into render — never a second full fetch of the same entities, never a state that can reorder the first list.
**When to use:** Whenever additional per-row data is "nice to have but shouldn't block first paint" — this is the exact justification the code comment on `EpicsPage.tsx` line 4-5 gives for why enrichment was previously skipped entirely; this phase now wires it in without violating that constraint.
**Example (adapted from `BacklogPage.tsx`'s `epicNames`/`epicColors` maps, and the target shape for this phase):**
```tsx
// Source: this codebase, BacklogPage.tsx epic-map pattern (existing) — epics.ts (see caveat below)
const epicKeys = epics.map((e) => e.key);
const {
  data: enrichmentMap,
  isError: enrichmentError,
  refetch: refetchEnrichment,
} = useQuery({
  queryKey: ['jira-epics-enrichment', epicKeys.join(','), jiraBaseUrl],
  queryFn: () => fetchEpicEnrichmentMap(jiraBaseUrl ?? '', token ?? '', epicKeys, storyPointsFieldKey, epicLinkFieldKey),
  enabled: !!jiraBaseUrl && !!token && epicKeys.length > 0,
});
// In EpicRow: const enrichment = enrichmentMap?.get(epic.key);
// enrichment === undefined && isLoading  -> skeleton shimmer (D-14)
// enrichmentError                        -> warning glyph + retry (D-15)
// enrichment.total === 0                 -> "No stories" (D-16)
// else                                   -> segmented bar + done/total + done/total SP
```
**IMPORTANT caveat:** the batched design means retry semantics are query-level, not per-epic — see Open Questions below regarding D-15's "re-firing just that epic's enrichment lookup" copy.

### Pattern 3: Segmented (multi-category) progress bar — no existing primitive, build small
**What:** A 3-segment horizontal bar built from 3 sibling `div`s inside a flex track, each sized by `${count/total*100}%` width, coloured via the existing status-category token vocabulary.
**When to use:** Exactly this phase's progress+breakdown visual (D-11) — `base-ui`'s `Progress` component is single-fill (`ProgressIndicator` has one `width: calc(var(--progress-value)*1%)`), confirmed by reading `src/components/ui/progress.tsx`.
**Example:**
```tsx
// New component — no direct source precedent in this codebase, colours sourced from:
// Source: src/lib/statusStyles.ts DOT_STYLES ('new'→gray-400, 'indeterminate'→blue-500, 'done'→green-500)
function EpicProgressBar({ done, inProgress, todo, total }: { done: number; inProgress: number; todo: number; total: number }) {
  if (total === 0) return <span className="text-xs text-muted-foreground">No stories</span>; // D-16
  const pct = (n: number) => `${(n / total) * 100}%`;
  return (
    <div className="flex items-center gap-1.5">
      <div
        className="flex h-1.5 w-16 overflow-hidden rounded-full bg-muted"
        title={`${done} Done · ${inProgress} In Progress · ${todo} To Do`}
      >
        <div className="bg-green-500" style={{ width: pct(done) }} />
        <div className="bg-blue-500" style={{ width: pct(inProgress) }} />
        <div className="bg-gray-400" style={{ width: pct(todo) }} />
      </div>
      <span className="text-xs text-muted-foreground tabular-nums">{done}/{total}</span>
    </div>
  );
}
```

### Anti-Patterns to Avoid
- **Reordering rows when enrichment lands:** Do not `.sort()` the merged array by any enrichment field — D-17/criterion 1 require the row order to come only from the basic query's JQL and never change afterward.
- **Full-cell overlay for the D-15 retry glyph:** Per the 91.1 CR-05 precedent (an inner cell swallowed row clicks across ~190px of every row), the retry target must be a small, precisely-bounded `<button>` with `e.stopPropagation()` on click — not an absolute-inset overlay.
- **Treating a caught/swallowed enrichment error as "0 stories":** This is the exact bug class D-15 exists to prevent (same class as `88-CR-01`/`91.1-CR-06`/`searchProjectTags` in 91-07) — the current `.catch(() => [])` in `fetchEpicEnrichmentMap` must be removed, not preserved.
- **Editing `src/services/jira/epics.ts`:** It is dead code from this page's (and every other page's) perspective — see Summary. Edits there will have zero runtime effect.

## Common Pitfalls

### Pitfall 1: Editing the wrong `epics.ts` (jira.ts dual-file gotcha)
**What goes wrong:** A plan/task edits `src/services/jira/epics.ts` (matching CONTEXT.md's canonical file list literally) and the running app shows no change at all.
**Why it happens:** `@/services/jira` resolves to the sibling **file** `src/services/jira.ts` before the **directory** `src/services/jira/`, because both exist and file-resolution wins over directory-index resolution. `src/services/jira/index.ts`'s barrel does not re-export `epics.ts`. `EpicsPage.tsx` and `EpicsPage.test.tsx` both reference `@/services/jira` (confirmed via `vi.mock('@/services/jira', ...)` in the existing test).
**How to avoid:** Make all fetcher edits in `src/services/jira.ts` (search for `// Phase 13 — Epic Management` comment, ~line 2408, to locate the section). Treat `src/services/jira/epics.ts` as legacy/duplicate and leave it alone (or note it for a future dead-code cleanup — out of scope here).
**Warning signs:** `grep -rn "from '@/services/jira/epics'" src` returns nothing outside `epics.test.ts` itself — that absence is itself the confirming signal.

### Pitfall 2: `<table>` layout collapsing new narrow columns to 0px in WebKit
**What goes wrong:** Adding priority/progress/points columns to the existing `<table>`/`<colgroup>` structure produces columns that render at 0 width in the Tauri/WebKit webview (not reproducible in jsdom/Vitest), per the app's own documented recurring bug class.
**Why it happens:** Automatic table layout in WebKit distributes width unpredictably once more narrow, unequal-content columns are added; this codebase has hit this exact failure mode multiple times (fixed previously via explicit-px sizing, e.g. `CachedAvatar`).
**How to avoid:** Convert `EpicRow` to the div+flex row shape used by `BacklogRow.tsx` (`flex-none` cells with explicit `w-*`/px widths, one `flex-1 min-w-0` cell for the name). This sidesteps table layout entirely.
**Warning signs:** Any column rendering at 0 width or invisible content only in the real app, not in tests — must be verified manually in the Tauri webview at all 3 densities, not just visually inspected in jsdom.

### Pitfall 3: Batched enrichment retry semantics don't match the "retry just this epic" copy
**What goes wrong:** D-15's UI copy says the retry click "re-fires just that epic's enrichment lookup," but `fetchEpicEnrichmentMap` is one batched call for ALL epic keys — there is no per-epic fetch to selectively retry.
**Why it happens:** The enrichment fetcher's design (one JQL batch call for N epics) trades per-row error granularity for request-count efficiency. A true "retry only this epic" would require either a new single-epic fetcher or accepting that retry re-fires the shared batched query for everyone.
**How to avoid:** Flagged as an Open Question below — the planner must pick one of: (a) retry re-fires the whole batched enrichment query (simplest, matches existing fetcher signature, only cosmetic mismatch with the word "just"), or (b) add a lightweight single-key variant of `fetchEpicEnrichmentMap` for per-row retry. Given "Claude's discretion" is not granted here (D-15 is a locked decision, only its exact retry mechanics are underspecified), default to (a) unless the planner has reason to add (b).
**Warning signs:** A UAT step that clicks retry on epic A and expects epic B's already-failed cell to remain in the failure state — under option (a) it will also refetch and may recover/fail again.

### Pitfall 4: `statusPillClass` without a flex wrapper
**What goes wrong:** The pill's `min-w-[5.5rem]`/`text-center` (from `STATUS_PILL_LAYOUT_CLASS`) silently collapse if the pill's parent is a bare `<span>`/inline context instead of a flex container.
**Why it happens:** `statusPillClass` assumes a flex-item context (documented in the function's own JSDoc and in the current `EpicRow`'s existing `<div className="flex">` wrapper).
**How to avoid:** Keep the existing `<div className="flex">` wrapper around the status pill when converting the cell to the new div+flex row shape.

### Pitfall 5: `EpicEnriched` type / `fetchEpicsBasic` not requesting `priority`
**What goes wrong:** Rendering `<PriorityIcon priority={epic.priority} />` produces nothing because `priority` was never in `epicFields` or the mapped return object.
**Why it happens:** `fetchEpicsBasic`'s current `epicFields` list is `['summary', 'status', 'assignee', epicNameFieldKey, epicColorFieldKey]` — no `'priority'`. `fetchEpicsWithEnrichment` (the unused sibling fetcher) DOES fetch `'priority'`, showing the field key is correct (`'priority'`, a system field, not a customfield) — it just needs porting into `fetchEpicsBasic`.
**How to avoid:** Add `'priority'` to `fetchEpicsBasic`'s `epicFields`, add `priority: epic.fields.priority` to the mapped return, and add `priority?: { name?: string; iconUrl?: string } | null` to the `EpicEnriched` interface (both the one in `services/jira.ts` and — for consistency only, since it's otherwise unused — the duplicate in `services/jira/types.ts`/`services/jira/epics.ts`).

## Code Examples

### Adding per-status-category counts + donePoints to the enrichment aggregation
```ts
// Source: this codebase, src/services/jira.ts fetchEpicEnrichmentMap — extend the existing loop
const countMap = new Map<
  string,
  { total: number; done: number; inProgress: number; todo: number; points: number; donePoints: number }
>();
for (const story of stories) {
  const ek = story.fields[epicLinkFieldKey] as string | null;
  if (!ek) continue;
  const entry = countMap.get(ek) ?? { total: 0, done: 0, inProgress: 0, todo: 0, points: 0, donePoints: 0 };
  entry.total++;
  const catKey = story.fields.status.statusCategory?.key; // 'new' | 'indeterminate' | 'done'
  const sp = (story.fields[storyPointsFieldKey] as number | null) ?? 0;
  entry.points += sp;
  if (catKey === 'done') {
    entry.done++;
    entry.donePoints += sp;
  } else if (catKey === 'indeterminate') {
    entry.inProgress++;
  } else {
    entry.todo++;
  }
  countMap.set(ek, entry);
}
return countMap;
```
