# Phase 91.1 Plan 09: Two filtering warning badges replace the single flagged-count integer Summary

**`⚠ N wrong branch` and `⚠ N no milestone` orange work-queue badges (click-to-filter, toggle-off, escape-hatch notice) replace the single neutral `flagged-count-badge` integer, closing UAT-91.1-B and recording IN-04's multi-key counting decision in code.**

- **Tasks:** 3 completed
- **Files modified:** 7

## Accomplishments
- `countBranchFlaggedMRs`/`countMilestoneFlaggedMRs` added beside `countBrMsFlaggedMRs`, each counting its own predicate independently; Rule 1 (double-flag sum can exceed the union) and Rule 2 (multi-key dedup) stated verbatim in a shared docstring and enforced by 5 new tests
- `useReleaseDetail` derives and returns `brFlaggedCount`/`msFlaggedCount` from `driftRows`, threaded through `ReleaseDetailPage.tsx` to `UnifiedTaskTable`; 2 new hook-level tests assert the per-category counts at the hook boundary, including the double-flag case where the union stays 1 but each badge counts 1
- The single `flagged-count-badge` (`variant="secondary"`, read as a second progress metric) is gone. Two `variant="outline"` orange warning badges (`flagged-br-badge`, `flagged-ms-badge`) render only when their count is > 0, each clickable (`aria-pressed` toggle) to filter `primaryRows`/`secondaryRows` to that category at render time
- A double-flagged MR remains visible under either filter (Rule 1 at the UI boundary); an MR attached under two fix-version tasks still counts once per badge while rendering under both tasks (Rule 2 at the UI boundary)
- `filter-active-notice` + `filter-clear` escape hatch covers the case where a successful fix drops a count to zero and hides its own badge
- While a filter is active, filtered-out task rows are dropped entirely (not rendered with an empty `MrSlot`), so `mr-slot-pending`/`-none`/`-unavailable`/`-failed` never leak through the filter
