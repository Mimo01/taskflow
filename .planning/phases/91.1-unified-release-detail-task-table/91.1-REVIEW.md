# Phase 91.1: Code Review Report

**Reviewed:** 2026-08-12
**Depth:** standard
**Files Reviewed:** 7
**Status:** issues_found

## Summary

The partition logic (`buildTaskMrAttachment`) and the flagged-count dedup semantics
(`countBrMsFlaggedMRs`) are correct as specified: the two partitions really are total and
disjoint (the `taskKeys ∩ coveredKeys` rule is the complement of the per-issue
`taskKeys.includes(issue.key)` filter, and both sides read the same key set built from the
same `releaseIssues`), the `taskReason`-vs-`taskKeys` trap called out in the docstring is
genuinely avoided, and neither function mutates its inputs. Row-order stability across a
successful BR/MS fix — the thing the deleted `applyHeldOrder` freeze existed to protect —
also survives the merge by construction: primary sub-lines are iid-ascending, and every
evaluated secondary row keeps `task === 'flag'` permanently, so a fixed row never crosses
the flagged/clean sort boundary. All 109 tests in the three suites pass.

The defects are concentrated in one place the merge did not carry over: **settled-state
derivation**. `UnifiedTaskTable` now renders three affirmative negative claims — the
secondary "not in fix version" table, the per-task "⚠ No merge request" line, and the
"— MR status unavailable" line — and all three are gated on `isLoading` flags that do not
cover (a) the Jira issue query, (b) the GitLab milestone query, or (c) any query *failure*.
The result is user-facing statements of fact derived from data that has not arrived or never
will. This is the same "an unqueryable channel must not terminate as a settled negative"
rule the sibling merge-back code in `useReleaseDetail.ts` states three separate times in its
own comments (CR-03/WR-04), applied inconsistently to the new table. The rest is dead code
and contract drift left behind by the component deletion.

Per instruction, the two known DESIGN gaps recorded in `91.1-UAT.md` (table visual clutter,
bare-integer flagged badge) are excluded.

## Critical Issues

### CR-01: Secondary table asserts "not in fix version" while the fix-version issue list is still loading

**File:** `taskflow/src/routes/dashboard/release-detail/UnifiedTaskTable.tsx:656-691`
(with `taskflow/src/routes/dashboard/release-detail/useReleaseDetail.ts:556,573`)

**Issue:** The secondary section is rendered on `secondaryRows.length > 0` alone — it sits
*outside* the `isLoadingIssues` branch that guards the primary table. While
`fetchFixVersionIssues` is in flight, `releaseIssues` is `[]`, so `fixVersionIssueKeys` and
`coveredKeys` are both empty and **every** MR that Channel B/C already returned is
classified as uncovered. The user sees "Loading issues…" above a fully populated
"Not covered by tasks above" table whose every row carries an orange warning glyph and the
tooltip `"PROJ-9 is not in fix version 33.5.0"` — a factual claim about a fix version whose
contents have not been fetched. When the issue query resolves, most of those rows silently
jump up into the primary table.

Confirmed by direct render (probe, since removed): with `isLoadingIssues: true`,
`secondaryRows: [row]`, the component renders `Loading issues...`, `secondary-section`, and
`secondary-key-flagged` with `title="PROJ-9 is not in fix version 33.5.0"` simultaneously.
No existing test covers `isLoadingIssues: true` together with a non-empty `secondaryRows` —
`D-13: secondary table` only exercises the loaded state.

Note this is the same class of defect the UI-SPEC calls a hard constraint for the MR-slot
("States 2 and 3 must never render while state 1's condition holds … the checker should
treat a flash of state 2/3 before MR data resolves as a defect"); the secondary table simply
was not covered by that rule's wording.

**Fix:** Gate the whole secondary section on issues having settled, and suppress the
flagged-count badge in the same window so it does not report a settled `0`/partial total:

```tsx
{!isLoadingIssues && secondaryRows.length > 0 && (
  <div data-testid="secondary-section" className="mt-4 pt-4 border-t border-border/50">
```

Add a regression test asserting `queryByTestId('secondary-section')` is null when
`isLoadingIssues` is true and `secondaryRows` is non-empty.

### CR-02: "No merge request" / "MR status unavailable" are asserted from unsettled and failed queries

**File:** `taskflow/src/routes/dashboard/release-detail/UnifiedTaskTable.tsx:516-550`
(with `taskflow/src/routes/dashboard/release-detail/useReleaseDetail.ts:136-142,576-577`)

**Issue:** `MrSlot` treats `isLoadingDrift === false` as "the MR question has been answered",
but `isLoadingDrift = isLoadingChannelA || isLoadingChannelB || isLoadingChannelC` models
neither failure nor the milestone query. Two reachable false negatives result:

1. **Channel failure ⇒ "⚠ No merge request".** `useReleaseDetail` never destructures
   `isError` from the three channel queries. When `fetchAllProjectMRs` /
   `fetchMilestoneMRs` / `fetchBranchTargetedMRs` reject (401 after PAT rotation, 5xx,
   timeout), `data` is `undefined` and `isLoading` is `false`, so `driftRows` is empty and
   **every task row** renders the orange `mr-slot-none` "No merge request" warning. The user
   is told, in orange, that a verified check found nothing — when no check completed.

2. **Milestone query pending ⇒ "— MR status unavailable" + degraded banner.**
   `hasMatchedMilestone` is `matchedMilestone !== null`, and `resolveGitLabMatch` returns
   `null` both for "no milestone matches" and for "`milestones` is still `undefined`"
   (`releaseSummaries.ts:67`). The milestone query's loading state is not part of
   `isLoadingDrift` (and is not returned by the hook at all), so whenever
   `gitlab-milestones` resolves after the drift channels — trivially reproducible with the
   Channel A result warm in cache and the milestone list stale — the table paints the D-16
   degraded banner and a per-task "MR status unavailable" for a release that does have a
   matched milestone.

This is precisely the CR-03/WR-04 rule the same hook enforces for the tag and tracking-MR
channels ("A channel that cannot be queried at all is a check that did not happen, so it
terminates as a FAILURE"), not applied to the three MR channels feeding the new table.

**Fix:** Make the MR-slot state a tri-state that distinguishes *unanswered* from
*answered-empty*. In `useReleaseDetail`:

```ts
const { data: allProjectMRs, isLoading: isLoadingChannelA, isError: channelAFailed } = useQuery(...)
// ...same for B and C, plus the milestone query:
const { data: allProjectMilestones, isLoading: isLoadingMilestones } = useQuery(...)

const isLoadingDrift = isLoadingChannelA || isLoadingChannelB || isLoadingChannelC || isLoadingMilestones;
const driftUnavailable = channelAFailed || channelBFailed || channelCFailed;
```

and in `MrSlot`, render a neutral "couldn't check merge requests" line (never the orange
`mr-slot-none`) when `driftUnavailable` is true, exactly as `mr-slot-unavailable` already
does for the no-milestone case.

## Warnings

### WR-01: `handleNavigateToIssueFromMR` pushes a duplicate breadcrumb entry

**File:** `taskflow/src/routes/dashboard/ReleaseDetailPage.tsx:180-185`

**Issue:** `seedReleaseBreadcrumb` (lines 159-166) is deliberately idempotent — it checks
whether the trail's last entry is already `/release/${versionId}` before pushing.
`handleNavigateToIssueFromMR` duplicates the push without that guard. Reproducible sequence:
click a task row → `onSeedBreadcrumb()` fires and pushes `/release/5` (the peek panel opens,
no navigation) → close the peek → click a ticket key inside an MR sub-line title →
`breadcrumbPush({ path: '/release/5' })` runs unconditionally. The trail now contains the
release twice and the breadcrumb header renders "… > 33.5.0 > 33.5.0". The unified table
makes this easier to hit than before, because task rows and linkified MR titles now live in
one interleaved list.

**Fix:** Reuse the guarded helper instead of re-implementing the push:

```tsx
const handleNavigateToIssueFromMR = (key: string) => {
  seedReleaseBreadcrumb();
  navigate(`/issue/${key}`);
};
```

### WR-02: `matchIssuesToMRs` is now dead, untested, exported code

**File:** `taskflow/src/routes/dashboard/release-detail/releaseSummaries.ts:114-135`

**Issue:** Deleting `buildIssueMrIndex` removed the last caller of `matchIssuesToMRs`. A
repo-wide grep finds exactly one occurrence — its own definition. It is not referenced by
`releaseSummaries.test.ts` either, so it is an exported, unreferenced, uncovered function
that still pulls in `linkMRToTask` and encodes the superseded one-MR-per-issue matching rule
the phase deliberately replaced. Leaving it exported invites a future caller to reintroduce
the old semantics.

**Fix:** Delete `matchIssuesToMRs` (and its now-unused `unmatched` return shape) from
`releaseSummaries.ts`; the phase already deleted `IssuesSection`/`MrDriftSection`, this is
the same cleanup one level down.

### WR-03: `DriftRow.task` / `taskReason` are now write-only, and the module contract documenting them is stale

**File:** `taskflow/src/routes/dashboard/release-detail/driftDetection.ts:25-27,49-51,265-266`

**Issue:** The TASK column was dropped from the presented grid (UI-SPEC, criterion 4). No
production code now reads `row.task` or `row.taskReason` — only the test suites and
`buildDriftRows`'s own local `flagged` computation do. Meanwhile the module header still
states the D-12 rationale as "**the two reasons are distinguishable … so the UI tooltip can
explain which case applies** — do not collapse to a boolean", and `countBrMsFlaggedMRs`'s
docstring reasons about `row.flagged`, which is likewise only used as a sort key now. A
reader trusting these comments will look for a TASK tooltip that no longer exists, and the
"do not collapse" instruction now protects nothing.

**Fix:** Either (a) update the D-12 comment to state that `taskReason` is retained solely
for the secondary-table key cell / future re-introduction, and have the secondary key cell
actually consume it (see WR-04), or (b) drop `task`/`taskReason` from `DriftRow` along with
their tests. Do not leave the comment asserting a consumer that was deleted.

### WR-04: Secondary key cell re-derives task drift from `taskKeys` instead of the row's own verdict, and reads the array before its guard

**File:** `taskflow/src/routes/dashboard/release-detail/UnifiedTaskTable.tsx:660-679`

**Issue:** Three problems in one block:

1. `const key = row.taskKeys[0];` is read one line *before* the `row.taskKeys.length > 0`
   guard that makes it safe. It happens to work (the guard is checked before `key` is
   interpolated), but it types as `string` while being `undefined` at runtime for keyless
   rows — one refactor away from rendering `"undefined is not in fix version 33.5.0"`.
2. The orange/neutral decision is re-derived from `taskKeys.length` rather than from
   `row.taskReason`, which is the field the data layer computed for exactly this purpose.
   For a non-evaluated row (merged/closed/locked MR — `task: 'na'`, `taskReason: null`) with
   out-of-scope keys, the cell asserts a TASK drift the row itself marks as not evaluated.
   The two derivations can only stay consistent by accident.
3. Only `taskKeys[0]` is ever shown or named in the tooltip. An MR carrying two out-of-scope
   keys silently reports one, and which one depends on title-vs-branch extraction order.

**Fix:** Drive the cell from the row's verdict and name all keys:

```tsx
const keys = row.taskKeys;
const keyCell = keys.length > 0 ? (
  <span
    data-testid="secondary-key-flagged"
    title={`${keys.join(', ')} ${keys.length > 1 ? 'are' : 'is'} not in fix version ${versionName}`}
    /* … */
  >
    <AlertTriangle className="size-3" />
    {keys[0]}{keys.length > 1 ? ` +${keys.length - 1}` : ''}
  </span>
) : (/* … em dash … */);
```

### WR-05: The merge dropped every column label and the table semantics `IssuesSection` had

**File:** `taskflow/src/routes/dashboard/release-detail/UnifiedTaskTable.tsx:304-319`

**Issue:** `IssuesSection` rendered a real `<table>` with a `<thead>` labelling Key /
Summary / Assignee / Status / MR. `ColumnHeaderStrip` replaces it with a `bg-muted/30` strip
whose first four columns are **empty `<span>`s** — only `BR` and `MS` carry text. So the
unified table has no visible column labels for four of six columns, renders an otherwise
blank grey bar, and — because the div+flex structure carries no `role="table"`/`"row"`/
`"columnheader"` — offers no cell/column association to assistive technology either. The
div+flex structure itself is mandated by the UI-SPEC (Row anatomy: "not `<table>`"), but the
spec's typography table still budgets for "column header labels", so the blank spans look
like an unfinished re-host of `MrDriftSection`'s strip rather than a decision.

**Fix:** Label the strip's columns (`Key` / `Summary` / `Assignee` / `Status`), or, if the
labels are intentionally omitted for density, add ARIA table semantics so the information is
still exposed:

```tsx
<div role="row" className="...">
  <span role="columnheader" className={COL_KEY}>Key</span>
  <span role="columnheader" className={COL_SUMMARY}>Summary</span>
  {/* … */}
</div>
```

## Info

### IN-01: `extractMrTaskKeys` docstring promises deduplication it does not perform

**File:** `taskflow/src/routes/dashboard/release-detail/driftDetection.ts:150-156`
**Issue:** `@returns deduplicated keys from title then source_branch`, but the implementation
is a bare spread of two arrays. `extractTicketKeys` dedups *within* a string, not across the
two, so the common case (`title: "PROJ-1 fix"`, `source_branch: "feature/PROJ-1"`) yields
`['PROJ-1', 'PROJ-1']`. Harmless for the current `includes`/`some` consumers, but any future
consumer that counts or renders `taskKeys` inherits a duplicate.
**Fix:** `return [...new Set([...extractTicketKeys(mr.title), ...extractTicketKeys(mr.source_branch)])];`

### IN-02: MR title linkification re-derives ticket keys the row already carries

**File:** `taskflow/src/routes/dashboard/release-detail/UnifiedTaskTable.tsx:352`
**Issue:** `driftDetection.ts:148-150` describes `extractMrTaskKeys` as "the single source of
truth shared by `evaluateTaskDrift` and the UI tooltip … so neither re-derives it
independently", yet `MrSubLine` calls `extractTicketKeys(mr.title)` again. The two sets
legitimately differ (the row's list also includes branch-only keys), so the comment's claim
is simply no longer accurate for this component.
**Fix:** Either narrow the docstring to what it really guarantees, or store title keys and
branch keys separately on `DriftRow` so the component consumes rather than re-derives.

### IN-03: The flagged-count badge reports a settled total before the data settles

**File:** `taskflow/src/routes/dashboard/release-detail/UnifiedTaskTable.tsx:591-598`
**Issue:** The badge is unconditional, so it renders `0` while the drift channels are in
flight and a partial count while only some channels have resolved. (Distinct from the known
UAT-91.1-B presentation gap — this is about *when* the number is truthful, not how it looks.)
**Fix:** Render the badge only when `!isLoadingDrift && !isLoadingIssues`; fold into the
CR-01/CR-02 settled-state work.

### IN-04: A multi-key MR shows two orange rows but counts once in the badge

**File:** `taskflow/src/routes/dashboard/release-detail/driftDetection.ts:339-361`,
`taskflow/src/routes/dashboard/release-detail/UnifiedTaskTable.tsx:635-651`
**Issue:** D-15's union semantics are implemented correctly and deliberately, but the visible
consequence is that an MR attached under two fix-version tasks renders two flagged rows while
`flaggedMrCount` increments by one. Both copies also own independent `useMrFixMutation`
instances, so a failure on one leaves the twin looking actionable (asserted by the D-09
duplication tests). Worth making explicit in the follow-up that splits the badge — the UAT
note already flags the analogous BR+MS double-count decision.
**Fix:** No code change required now; record the multi-key case alongside the BR/MS case in
the badge-split follow-up so the counting rule is chosen, not inherited.
