## Assessment: Does the Code Review's Blockers Undermine the Phase Goal?

Both `91.1-REVIEW.md` blockers were independently re-confirmed by direct code inspection in
this verification pass (not merely trusted from the review document):

- **CR-01** (secondary section renders outside `isLoadingIssues` guard) — confirmed at
  `UnifiedTaskTable.tsx:656`.
- **CR-02** (`isLoadingDrift` models neither channel failure nor the milestone query) —
  confirmed at `useReleaseDetail.ts:503,518,536,576` (no `isError` destructured on any of the
  three channel queries; milestone query's loading state absent from `isLoadingDrift`).

These are not follow-up polish. They directly falsify roadmap success criteria 4 and 5 as
literally stated — a "Missing MR" state that can appear when the check did not actually run
(query in flight or failed) is not "surfacing its Missing MR state," it is surfacing a false
claim; a secondary table that transiently includes MRs correctly belonging to the primary
table is not "listing only MRs not covered by the primary table." The structural
replacement of the two old sections (criteria 1, 2, 6) is solid and fully verified. The
per-MR corrective-action re-hosting (criterion 3) is solid and thoroughly tested. The two
failing criteria are narrowly scoped to settled-state derivation, but they are must-haves,
not nice-to-haves — a user hitting a slow Jira fetch or a rotated/expired GitLab PAT will see
factually wrong drift claims on real data, which is exactly the class of defect this phase
exists to eliminate (the old sections had the same defect class addressed by Phase 89's
CR-03/WR-04 rule; this phase's new table does not yet inherit that rule for its own channels).

This is distinct from and additional to the two DESIGN gaps already recorded in
`91.1-UAT.md` (visual clutter, uninformative badge), which remain correctly routed to
follow-up work and are not repeated as gaps here.

### Gaps Summary

One grouped gap, two root causes, both in "settled-state derivation" (per the review's own
framing): (1) the secondary table's rendering guard omits `isLoadingIssues`, producing
transient false "not in fix version" claims; (2) `isLoadingDrift` omits channel-query
`isError` and the milestone query's own loading state, producing false "No merge request" /
"MR status unavailable" claims when a channel fails or the milestone query resolves out of
order. Both are small, mechanical fixes (add `isError`/`isLoading` destructuring, extend one
boolean gate, add one regression test each) confined to `useReleaseDetail.ts` and
`UnifiedTaskTable.tsx`. No architectural rework needed — the review already supplies the
exact diff.
