## Gaps

### UAT-91.1-A — Table is visually cluttered

status: failed
severity: design
verbatim: "works but it is very cluttered in the table. too much visual noise."

**Diagnosis.** Every MR sub-line renders the full cell set — iid, title, author avatar +
name, state pill, BR cell, MS cell — at the same visual weight regardless of whether the MR
has a problem. At real data density (a task with 2-4 MRs, most of them healthy) the eye has
no way to find the rows that actually need action. The row separators compound it: a border
between every row, including between sub-lines of the same task, so the grouping the
indentation implies is fought by the borders.

**Agreed fix direction (developer, 2026-08-12) — three changes, all in `UnifiedTaskTable.tsx`:**

1. **Quiet the healthy rows.** Keep every row visible — nothing is hidden behind a click —
   but strip color and weight from MR sub-lines with no BR/MS problem: no state-pill chrome,
   muted author text without the avatar chip treatment, plain glyphs. Only rows with an
   orange BR or MS cell keep full-strength color. Explicitly rejected: collapsing healthy
   MRs behind a "N more, all OK" affordance — the developer chose visible-but-quiet over
   hidden.
2. **Drop columns from sub-lines.** MR sub-lines stop rendering the author avatar+name and
   the state pill as dedicated columns; that information moves to the hover tooltip.
   Sub-lines become iid + title + status glyphs. Frees roughly a third of the sub-line width
   for the title, which currently truncates early.
3. **Lighter row separators.** Separators only between task groups, not between every
   sub-line of the same task. Pure CSS, no structural change.

### UAT-91.1-B — Flagged-MR count is an uninformative number

status: failed
severity: design
verbatim: "the number of mr's needing attention should be somehow reworked, it is just a not
telling number (the tooltip is there but that is not enough)"

**Diagnosis.** `UnifiedTaskTable.tsx:591-598` renders the count as
`<Badge variant="secondary" title="Merge requests needing attention">{flaggedMrCount}</Badge>`
— a bare integer in the neutral secondary variant, sitting immediately beside the
`{issuesFixed} / {issuesTotal} done` badge. It therefore reads as a second progress metric
rather than a warning, and the only thing distinguishing it is a `title` tooltip that
requires a deliberate hover to discover. It also collapses two genuinely different defects
(wrong target branch vs. missing release milestone) into one undifferentiated total, so even
once read it does not tell you what to go do.

**Agreed fix direction (developer, 2026-08-12): split the count by problem type.**

- Replace the single badge with two: `⚠ N wrong branch` and `⚠ N no milestone`, each
  warning-styled rather than neutral secondary.
- Each badge is **clickable and filters the table** down to the MRs in that category.
- A badge whose count is zero is hidden entirely (not rendered as `0`).
- This supersedes the D-15 single-total presentation. The underlying
  `countBrMsFlaggedMRs` derivation stays valid as the deduplicated union but is no longer
  the only thing surfaced; the follow-up needs per-category counts alongside it, which is a
  data-layer addition in `driftDetection.ts` on the same pattern.

**Note on the deduplication rule:** `countBrMsFlaggedMRs` deliberately counts an MR once
even when both BR and MS are flagged. Split badges must decide whether such an MR appears in
both categories (sum > union total) or only the more severe one. The follow-up plan must
make this explicit rather than inheriting it by accident — the existing D-15 tests assert
union semantics and will not catch a wrong choice here.
