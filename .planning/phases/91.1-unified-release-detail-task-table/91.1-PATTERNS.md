**New attachment function — analog is `buildIssueMrIndex`'s signature/JSDoc shape** (`driftDetection.ts:296-347`), NOT its 1:1-join body:
```typescript
/**
 * Task↔MR attachment (D-09, replaces buildIssueMrIndex for presentation):
 * groups driftRows by intersecting each row's taskKeys against releaseIssues.
 * An MR whose taskKeys match multiple release issues appears under EVERY
 * matching task (D-09) — this is 1:N, not buildIssueMrIndex's 1:1 first-match
 * join, and is the reason that function cannot be reused/extended here.
 *
 * secondaryRows = driftRows whose taskReason !== null (uncovered by any task).
 *
 * @param releaseIssues - Jira issues in the release's fix version, in Jira's return order
 * @param driftRows - the full drift row list from buildDriftRows (already per-mr.id deduped)
 * @returns primaryRows (issue -> its N drift rows, Jira order preserved) and secondaryRows
 */
export function buildTaskMrAttachment(
  releaseIssues: JiraIssue[],
  driftRows: DriftRow[],
): {
  primaryRows: Array<{ issue: JiraIssue; mrs: DriftRow[] }>;
  secondaryRows: DriftRow[];
} {
  const primaryRows = releaseIssues.map((issue) => ({
    issue,
    mrs: driftRows
      .filter((row) => row.taskKeys.includes(issue.key))
      .sort((a, b) => a.mr.iid - b.mr.iid), // stable deterministic sub-order, not drift-driven (D-18)
  }));
  const secondaryRows = driftRows.filter((row) => row.taskReason !== null);
  return { primaryRows, secondaryRows };
}
```
Keep `buildDriftRows`'s existing internal sort (`driftDetection.ts:274-277`) untouched per Research's A3 — it is presentationally inert once `buildTaskMrAttachment` re-groups/re-sorts for display, and is locked as an unchanged predicate/provenance function.

**Delete** (D-18, not modify): `applyHeldOrder` (`MrDriftSection.tsx:12-41`) has no destination — it is not moved anywhere, it is removed along with the component it lived in.
