**Closed both BLOCKING verification gaps by adding a driftUnavailable terminal state for failed MR channels and gating the secondary-table/flagged-badge renders on isLoadingIssues, so no affirmative negative claim ("No merge request", "not in fix version", "MR status unavailable") can render from an unsettled or failed query.**

## Decisions Made
- `driftUnavailable` is a terminal failure state, deliberately not merged into `isLoadingDrift` — conflating them would spin the "loading merge requests…" line forever for a permanently-failing channel instead of surfacing the failure
- `mr-slot-failed` reuses the exact `text-muted-foreground` neutral treatment already established by `mr-slot-unavailable`, keeping only one visual language for "we don't know" states in this component
- Branch order in `MrSlot` (pending → failed → verified-empty → resolved) is load-bearing and directly asserted by Test 5 (`isLoadingDrift: true` wins over `driftUnavailable: true`)

## Deviations from Plan

None - plan executed exactly as written. The test was adjusted to assert Channel A (which is milestone-independent) fires and resolves while `isLoadingDrift` stays `true` purely from `isLoadingMilestones`, which is the precise CR-02 regression the task exists to lock in. No code change was needed; this is a test-shape clarification, not a behavior deviation.
