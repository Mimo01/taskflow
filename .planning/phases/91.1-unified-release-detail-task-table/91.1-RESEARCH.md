## Summary

Phase 91.1 replaces two sibling sections on `ReleaseDetailPage.tsx` — `IssuesSection.tsx` (a `<table>` of Jira issues with a single best-guess MR cell) and `MrDriftSection.tsx` (a div+flex list of all discovered MRs with BR/MS/TASK drift cells) — with one unified div+flex primary table keyed on Jira tasks, each with 0..N MR sub-lines, plus one secondary div+flex table for MRs not covered by any task. All underlying data/logic modules (`driftDetection.ts`, `useMrFixMutation.ts`, `mrChannelKeys.ts`, `releaseSummaries.ts`'s `matchIssuesToMRs`) are explicitly locked as unchanged by CONTEXT.md; the phase's real work is entirely in `useReleaseDetail.ts` (new task→MR[] attachment/partition derivation) and in the presentational layer (new merged component replacing both existing ones), plus deletion of `applyHeldOrder`/`orderRef`/`heldForVersion` (D-18) and the TASK column.

The central new piece of logic — explicitly called out in CONTEXT.md as a gap — is: today `matchedRows: Array<{ issue: JiraIssue; mr: GitLabMR | null }>` pairs an issue with **at most one** MR (built by `buildIssueMrIndex`/`matchIssuesToMRs`, which is a 1:1 first-match join). The new shape needs `issue → GitLabMR[]` (many MRs per task, and the same MR under multiple tasks per D-09), built directly from `DriftRow.taskKeys` (already computed per MR by `driftDetection.ts`'s `extractMrTaskKeys`/`evaluateTaskDrift`) rather than from `matchIssuesToMRs`'s single-match semantics. `matchIssuesToMRs` and `wrongMilestoneByKey`/`buildIssueMrIndex` become dead code for the presentational layer once this attachment model lands — CONTEXT.md flags `wrongMilestoneByKey` as "a superseded heuristic" that must not survive as a parallel truth alongside the channel-derived drift marks.

**Primary recommendation:** Build the new task↔MR attachment/partition entirely from `driftRows` (which already carries `taskKeys`, `taskReason`, `br`, `ms` per MR with correct provenance) — do not extend or reuse `matchIssuesToMRs`/`buildIssueMrIndex`'s 1:1 join. Add one new pure function (analogous to `driftDetection.ts`'s existing style) that groups `driftRows` by task key and computes the "uncovered" partition, then delete `buildIssueMrIndex`'s two exports from the presentational path once the new function's outputs replace them everywhere they were consumed.

### Pattern 1: Task→MR attachment via `taskKeys`, not `matchIssuesToMRs`

**What:** `DriftRow.taskKeys: string[]` (from `extractMrTaskKeys` = title keys + source_branch keys, deduped) is already computed for every MR in `driftRows`. Group `driftRows` by intersecting `taskKeys` against `releaseIssues` — for each issue, collect every `driftRow` where `issue.key` is in that row's `taskKeys`. A `driftRow` whose `taskKeys` intersects zero release issue keys (i.e. `taskReason !== null`) is "uncovered" and belongs to the secondary table.

**When to use:** This is the sole replacement for `matchedRows`/`wrongMilestoneByKey`. `matchIssuesToMRs`'s 1:1-join semantics (first match wins, no duplication) is the wrong shape for D-09 (an MR under two tasks must appear under BOTH).

**Example (illustrative, not existing code — to be written this phase):**
```typescript
// Source: derived from driftDetection.ts patterns already in the codebase
export function buildTaskMrAttachment(
  releaseIssues: JiraIssue[],
  driftRows: DriftRow[],
): {
  primaryRows: Array<{ issue: JiraIssue; mrs: DriftRow[] }>;
  secondaryRows: DriftRow[];
} {
  const primaryRows = releaseIssues.map((issue) => ({
    issue,
    mrs: driftRows.filter((row) => row.taskKeys.includes(issue.key)),
    // stable deterministic sub-order per CONTEXT discretion: sort by mr.iid
  }));
  // secondaryRows = uncovered: taskReason !== null (no-linked-task OR not-in-fix-version)
  const secondaryRows = driftRows.filter((row) => row.taskReason !== null);
  return { primaryRows, secondaryRows };
}
```
Note: `evaluateTaskDrift` already checks ALL extracted keys against `fixVersionIssueKeys` (`driftDetection.ts:170-175`) — `taskReason === null` means "at least one key is in the fix version," which is exactly the primary-table membership condition. This function should sit next to `buildDriftRows` in `driftDetection.ts` to stay pure/testable, matching the module's existing "React-free" design goal — though CONTEXT.md's canonical_refs technically says "derived [in useReleaseDetail.ts], not in the presentational component," which is satisfied either way (both are non-presentational). `[ASSUMED]` — the exact file placement is Claude's/planner's discretion; CONTEXT.md does not mandate one over the other, only that it isn't in the component.

### Pattern 2: Streaming state — three-way discriminant per task (D-17)

**What:** The MR-slot under each task row must render one of: (1) `loading merge requests…`, (2) `⚠ No merge request`, (3) `— MR status unavailable`, (4) actual MR sub-lines. States 1 vs (2/3) must never both be true.

**When to use:** `useReleaseDetail.ts` already computes `isLoadingChannelA`, `isLoadingChannelB`, `isLoadingChannelC`, and the combined `isLoadingDrift = isLoadingChannelA || isLoadingChannelB || isLoadingChannelC` (`useReleaseDetail.ts:582`). This single boolean is sufficient to gate state 1 for ALL tasks uniformly (all three channels feed every task's MR set) — a per-task pending flag is not needed since channel queries are project/milestone/branch-scoped, not per-task. `hasMatchedMilestone` (already computed, `useReleaseDetail.ts:583`) distinguishes state 2 (healthy, `hasMatchedMilestone === true`) from state 3 (degraded, `hasMatchedMilestone === false`) once `isLoadingDrift` is false and `mrs.length === 0`.

**Example:**
```typescript
// Illustrative — component-level render branch
{isLoadingDrift ? (
  <SubLine muted>loading merge requests…</SubLine>
) : task.mrs.length === 0 ? (
  hasMatchedMilestone
    ? <SubLine orange>⚠ No merge request</SubLine>
    : <SubLine gray title="No GitLab milestone matched — cannot check for MRs">— MR status unavailable</SubLine>
) : (
  task.mrs.map((row) => <MrSubLine key={row.mr.id} row={row} />)
)}
```

### Pattern 3: D-15 flagged-count dedup

**What:** Today `driftFlaggedCount = countFlaggedMRs(driftRows)` (`driftDetection.ts:291-293`) counts flagged **rows** — already deduped by `mr.id` because `driftRows` is one entry per unique MR `id` (from `unionMRs`, keyed by `mr.id`). The only change needed: confirm it counts BR-or-MS, not BR-or-MS-or-TASK, since TASK is dropped from the presented UI. ### Anti-Patterns to Avoid
- **Reusing `matchIssuesToMRs`/`buildIssueMrIndex` for the new attachment model:** these are 1:1-join, first-match-wins — structurally incompatible with D-09's "MR appears under every matching task" requirement. Do not extend their signature; write a new function.
- **Re-deriving per-task loading state:** there is no per-task MR fetch; all three channels are release-scoped, not task-scoped. A single `isLoadingDrift` gates all tasks' sub-line slots simultaneously — do not invent per-task pending tracking.
- **Table layout (`<table>`) for the unified grid:** D-01 explicitly rejects it, citing the project's own recorded lesson ("table layout syncs widths across all rows"). Confirmed applicable: `IssuesSection.tsx` today IS a `<table>` and is being replaced specifically because of this; `MrDriftSection.tsx` today IS already div+flex and is the shape to imitate.

## The D-11 Held-Order Workaround — What It Is And What Must Change

**Location:** `MrDriftSection.tsx:12-41` (`applyHeldOrder` function), `MrDriftSection.tsx:330-342` (component-level `orderRef`/`heldForVersion` usage), `MrDriftSection.tsx:73` (the `versionId` prop that drives it), `ReleaseDetailPage.tsx:259-260` (`key={versionId}` + `versionId={versionId}` props passed specifically to feed this mechanism).

**Mechanism (as it exists today, Phase 89 D-11):**
1. `buildDriftRows` (`driftDetection.ts:274-277`) sorts rows **flagged-first, then `mr.iid` descending** — a live, render-time sort. Since wrong-branch and missing-milestone flags co-occur constantly on the same MR, and fixing one flag changes `row.flagged`/the sort key on the *next* render, a row could jump position out from under the user's pointer mid-interaction (e.g., user clicks BR fix, row still flagged via MS re-sorts elsewhere, user's next click lands on a different row).
2. `orderRef = useRef<number[] | null>(null)` captures the incoming `mr.id` order **once**, on the first non-empty render.
3. `heldForVersion = useRef(versionId)` resets `orderRef.current = null` whenever `versionId` changes — because `ReleaseDetailPage` does NOT put a `key` on the route-level container that would force a full remount when navigating between two already-cached releases (the skeleton branch is skipped), so without this the held order would persist across an unrelated release (documented as the WR-09 bug this fixes).
4. `applyHeldOrder(rows, orderRef.current)` reorders the freshly-sorted `rows` to match the frozen `heldIds` order every render, appending any new/unknown ids last.
5. `MrDriftSection` is ALSO given `key={versionId}` at the call site (`ReleaseDetailPage.tsx:259`) as a **second, redundant** remount mechanism — belt-and-suspenders with the internal `heldForVersion` ref.

**Why D-18 makes it unnecessary:** The new primary table's order is **Jira's own return order** for tasks (never re-sorted — Jira order is inherently stable across renders, it doesn't depend on drift state at all). The secondary table's order is `driftRows`' natural union order filtered to uncovered rows — CONTEXT.md's Claude's Discretion section explicitly sets "a stable deterministic order (e.g. by `iid`)" for MR sub-line ordering, not a flagged-first live sort. **Nothing in the new design re-sorts based on drift state**, so there is no "row jumps under the user's pointer" failure mode to guard against, and the entire freeze mechanism has no job to do.

**What must change (concrete deletions):**
1. Delete `applyHeldOrder` function (`MrDriftSection.tsx:12-41`) and its associated JSDoc.
2. Delete the `orderRef`/`heldForVersion` refs and the `if (heldForVersion.current !== versionId) {...}` / `if (orderRef.current === null && rows.length > 0) {...}` blocks (`MrDriftSection.tsx:330-341`).
3. Delete the `versionId` prop from the component's interface (`MrDriftSection.tsx:73`) — the new unified component may still legitimately need something version-scoped for OTHER reasons (e.g., if per-cell fix state must reset across releases — verify this is not actually needed for a different reason before dropping `key={versionId}` at the call site entirely; `useMrFixMutation` state is per-hook-instance and instances unmount/remount when their owning row disappears from the DOM, so cross-release staleness of *fix* state may not depend on this mechanism at all — `[ASSUMED, low risk]` this should be verified against `useMrFixMutation.test.tsx` during planning, not blindly carried over).
4. Delete or heavily rewrite the corresponding tests in `MrDriftSection.test.tsx` that assert held-order behavior (grep for `applyHeldOrder`, `orderRef`, `heldForVersion`, `WR-09` in that file during planning — not enumerated line-by-line here since the whole file is being restructured into the new component's test file anyway).
5. **Also drop the live flagged-first/iid-desc sort itself** from whatever function replaces `buildDriftRows`'s row-ordering for presentation purposes — D-18 requires "Jira order" for the primary table (trivially: iterate `releaseIssues` in their returned order) and "stable deterministic, not drift-driven" for secondary-table/sub-line order. `buildDriftRows`'s existing `rows.sort(...)` (`driftDetection.ts:274-277`) is explicitly locked as an unchanged predicate/provenance function per CONTEXT's "Out of scope" list ("any change to the drift predicates themselves... beyond what removing the presented TASK column requires") — **this sort is NOT a predicate, it's presentation ordering that leaked into the data layer**, so the safest reading is: leave `buildDriftRows`'s internal sort alone (nothing consumes `DriftRow[]` order-sensitively anymore once the new attachment function re-groups/re-sorts it for display), and do the D-18-compliant ordering entirely in the new attachment function / component. `[ASSUMED — flag to planner: confirm whether buildDriftRows's sort is truly dead weight post-91.1, or whether it should be simplified since its only consumer's ordering requirement changes]`.

## Common Pitfalls

### Pitfall 1: `<table>` layout re-syncs column widths across ALL rows
**What goes wrong:** Using a native `<table>` (as `IssuesSection.tsx` does today) for the unified grid would make every task row's AND every MR sub-line's column widths mutually dependent — a long MR title in one sub-line would force every task-row summary column to the same width, breaking the truncation UI-SPEC.md specifies per-line-type (task rows `text-sm`/`line-clamp-1`, MR sub-lines `text-xs`/`truncate`).
**Why it happens:** Table layout algorithm computes column widths from the union of all cell content in that column, across all rows, in one pass.
**How to avoid:** D-01 already resolves this — div+flex rows with explicit `w-[Npx]`/`flex-1 min-w-0` spans per column, exactly mirroring `MrDriftSection.tsx`'s existing header-strip geometry (`MrDriftSection.tsx:385-406`). Confirmed directly relevant: this is the exact documented project lesson (`feedback_table_vs_flex_rows.md` per user memory) and UI-SPEC.md cites it explicitly.
**Warning signs:** Any row's text suddenly truncating shorter than expected after adding a long-content sibling row elsewhere in the table.

### Pitfall 2: Zero-width column collapse in WebKit/Tauri for narrow flex-none columns
**What goes wrong:** Narrow `flex-none` columns (the 28px BR/MS gutters, the 20px avatar) can collapse to 0 width in this app's WebKit/Tauri webview when sizing is implicit rather than explicit.
**Why it happens:** Documented project pattern (`project_virtualized_table_zero_width_col.md` per user memory) — narrow columns collapse to 0 in position:absolute-row tables in this specific WebKit/Tauri combination.
**How to avoid:** Both source files already use explicit px (`w-[28px]`, `size={20}` on `CachedAvatar`) — UI-SPEC.md's Spacing Scale section explicitly calls these out as "carried verbatim... do not round to the 8pt scale." The pitfall is only live if a future edit changes these to a relative unit (`%`, unconstrained `flex-1` on a narrow column) — not currently at risk since D-02's shared grid reuses the existing explicit widths.
**Warning signs:** BR/MS icons or avatars invisible/misaligned specifically in the Tauri build (may render fine in a browser dev server, since this is a WebKit-specific quirk).

### Pitfall 3: `statusPillClass` collapses on a bare inline `<span>`
**What goes wrong:** The pill's `min-w`/`text-center` Tailwind classes silently collapse when applied directly to an inline `<span>` inside a `<td>` (today's usage, `IssuesSection.tsx:127`) rather than a flex-display parent.
**Why it happens:** Documented project lesson (`project_statuspill_needs_flex_parent.md`) — `min-w` has no effect without a flex/grid layout context establishing it as a real sizing constraint.
**How to avoid:** UI-SPEC.md's Component & Layout Contract explicitly requires wrapping in "a flex div, per the recorded pill-needs-flex-parent lesson" — confirmed as directly applicable since the status pill moves from a `<td>` context to a `div`+flex column context in the new component; the wrapping requirement carries forward unchanged.
**Warning signs:** Status pill text overflowing its intended pill background, or the pill not centering.

### Pitfall 4: Overlay-button pattern required for task-row full-click + nested key button
**What goes wrong:** `div[role=button]` wrapping a nested real `<button>` (the naive way to make "click anywhere on the row" coexist with "but the key specifically opens the full issue") creates invalid/confusing nested-interactive-element semantics and event-handling conflicts.
**Why it happens:** Documented project lesson (`project_overlay_button_nested_interactive.md`) from prior full-row-click + inner-key-button work elsewhere in this codebase.
**How to avoid:** D-04 mandates the recorded pattern explicitly: an `absolute inset-0` `<button>` as a **sibling** of the key `<button>`, never a wrapper. `IssuesSection.tsx` today uses a `<tr onClick>` + `stopPropagation()` on the inner key button (`IssuesSection.tsx:86-104`) — this pattern does NOT transfer directly to the new div+flex row (no `<tr>` click delegation available), so the overlay-button rewrite is a real, non-trivial part of this phase's row-anatomy work, not a copy-paste.
**Warning signs:** Keyboard tab order skipping the overlay button, or a click on the key text accidentally triggering both the peek AND the full-open handlers.

### Pitfall 5: `driftFlaggedCount`'s current definition includes TASK, which must be excluded post-91.1
**What goes wrong:** See "Pattern 3" above — if the planner naively re-wires `flaggedCount={driftFlaggedCount}` unchanged into the new header, the badge will overcount because every uncovered/secondary-table MR's `task` mark is always `'flag'` by D-11's enforced convention, and D-15 only wants BR-or-MS.
**Why it happens:** `countFlaggedMRs` (`driftDetection.ts:291-293`) counts `row.flagged`, which is `br === 'flag' || ms === 'flag' || task === 'flag'` (`driftDetection.ts:268`) — a definition that predates D-15's redefinition and predates TASK being dropped from the presented UI.
**How to avoid:** Introduce a BR-or-MS-only count at the call site or as a new small function; do not reuse `countFlaggedMRs`/`row.flagged` for the header badge without auditing this.
**Warning signs:** The header's flagged count doesn't match "distinct MRs with an orange glyph visible anywhere on screen" when manually counted during UAT.

### Pitfall 6: `MrDriftSection.test.tsx`'s load-bearing test-ids
**What goes wrong:** `drift-row`, `drift-br`, `drift-ms`, `drift-task`, `drift-degraded-banner` are explicitly called "load-bearing" in CONTEXT.md canonical_refs — renaming them is "a deliberate act requiring test updates in the same commit," not an incidental refactor side-effect.

**How to avoid:** Since `drift-task` corresponds to the now-deleted TASK column, that specific test-id necessarily disappears — this is expected and CONTEXT-sanctioned (criterion 4). `drift-row`, `drift-br`, `drift-ms`, `drift-degraded-banner` should be preserved on their functional equivalents (MR sub-line, BR cell, MS cell, degraded banner) in the new component unless the planner has a specific reason to rename, in which case tests must be updated in the same commit per the canonical_refs instruction.
