# Phase 91.1: Unified Release Detail Task Table - Context

**Gathered:** 2026-08-12
**Status:** Ready for planning

<domain>
## Phase Boundary

Release detail presents **one primary table keyed on Jira tasks** in the fix version, with every merge request for a task rendered as a stacked sub-line inside that task's block, carrying the Phase 90 BR/MS drift checks and corrective actions per MR. A **single secondary table** lists only the MRs the primary table does not cover. `IssuesSection.tsx` and `MrDriftSection.tsx` are **replaced**, not restyled.

**In scope:** the unified row/sub-line renderer and its column grid; re-hosting the P90 `DriftActionCell` / `DriftMarkCell` / `useMrFixMutation` behaviour onto MR sub-lines in both tables; task↔MR attachment logic (which MRs belong to which task, and which fall to the secondary table); the zero-MR and degraded-state sub-lines; the merged section header (progress + done badge + flagged count) and the single degraded banner; the streaming render (tasks at Jira speed, MR lines arriving later); deletion of the D-11 held-order mechanism and the TASK drift column from the presented UI.

**Out of scope:** any change to the drift **predicates** themselves (`driftDetection.ts`'s br/ms evaluation, `unionMRs`, channel discovery) beyond what removing the presented TASK column requires; any new corrective action (P89 D-11 — keyless MRs still get no "link an issue" action, and the planner must not invent one); bulk / "fix all" affordances; merge-back verification (Phase 91, shipped); branch/milestone creation (Phase 88, shipped); a Releases-list aggregate drift count (DRIFT-09 was built in P89 and removed at UAT — do not build for it).

**Carried forward and NOT re-litigated** — these are locked by Phases 89/90 and survive intact into the new row shape:
- P90 D-01/D-02: control is hover-revealed **inside** the 28px cell; row hover reveals, cell hover emphasizes. No trailing button column.
- P90 D-03/D-04/D-05: `GitBranch` / `Milestone` icons, focus-reachable `<button>`, only `flag` cells actionable.
- P90 D-06/D-07/D-08/D-09: pessimistic glyph (spinner → ✓ on server settle), red ⚠ with error tooltip and click-to-retry, sticky local error keyed `(mr.id, action)`, per-cell (not per-row) locking.
- P90 D-10: the object-keyed GitLab error extractor stays.
- P90 D-13: invalidate all three channel queries at **project** granularity on success.
- P90 D-14/D-15: inert flagged BR when the release branch doesn't exist; `—` when no milestone matched.
- P90 D-16: **no confirm dialog and no warning on retarget**, regardless of approval-reset consequences. Do not reintroduce friction.
- ROADMAP-locked at insert time: stacked sub-lines (not chips, not collapse-on-click); out-of-scope-key MRs go to the secondary table with the key shown; state badge required; `!iid` + linkified title + author carried; **actual target branch lives in the BR tooltip**, not its own column; Jira order, no drift-driven re-sort.

</domain>

<decisions>
## Implementation Decisions

### Row and sub-line anatomy

- **D-01 (user):** The primary table is **`div` + flex rows**, following `MrDriftSection`'s existing shape — a header strip of `flex-none`/`flex-1` spans, then one div per task row and one div per MR sub-line. Not a `<table>`. Rationale: table layout synchronises widths across *all* rows (the recorded "everything truncates at the same point" failure), and the two line types have genuinely different content pressure. The P90 28px cells with their hover/focus behaviour port over untouched. Add ARIA table roles if semantics are wanted; do not reach back for `<table>`.
- **D-02 (user):** **Shared column grid.** MR sub-lines reuse the *same* span widths as the task row — `!iid` in the key column, title in the summary column, author in the assignee column, state badge in the status column, BR/MS in the trailing gutter. Both line types scan vertically as one table.
- **D-03 (user):** **Indent + muted, no borders.** Task rows carry the `border-b` separator and normal weight; MR sub-lines are indented (~16px), one size smaller, muted-foreground, with **no border between sibling MR lines** — so a task plus its MRs reads as one visual block and separators mark task boundaries only. Rejected: a tint band (busy over a long release, fights hover states) and tree connectors (box-drawing glyphs appear nowhere else in the app).
- **D-04 (user):** **Task row is click-anywhere-to-peek; the MR sub-line is not.** The task row keeps today's full-row click to open the issue peek — implemented with the recorded overlay-button pattern (an `absolute inset-0` button as a **sibling** of the key button, never `div[role=button]` wrapping a nested `<button>`). MR sub-lines have **no line-wide click target**: their only interactive elements are `!iid` (opens GitLab), linkified ticket keys in the title, and the BR/MS cells.
- **D-05 (user, refines P90 D-02):** The P90 hover-reveal group scopes to the **individual MR sub-line**, not the task block. Hovering `!412` reveals only `!412`'s action icons; `!418`'s cells stay `⚠`. Reveal must not cascade from the task row.

### Task-row rollup and the zero-MR state

- **D-06 (user):** The **task row's BR/MS gutter renders empty**. No rollup glyph, no count chip. Drift is a per-MR fact and the flags sit in the same columns one line below; a rollup would restate visible information and make the same glyph mean "act here" on one line and "look below" on another. Rejected: worst-of rollup, flagged-count badge.
- **D-07 (user, satisfies criterion 4):** A task with **zero MRs** renders exactly one muted sub-line in the slot where MRs would be: **`⚠ No merge request`** in orange-muted. Every task therefore has at least one line beneath it and the parent/child rhythm never breaks.
- **D-08 (user, hard):** In the **degraded state** (no matched GitLab milestone, so channels B and C cannot run) the zero-MR line is **visually and semantically distinct**: a neutral grey **`— MR status unavailable`** with a tooltip explaining that no milestone matched and only Jira-linked MRs could be found. It must **never** render the orange `⚠ No merge request`, because the app did not verify absence — it was unable to check. This mirrors today's `IssuesSection` behaviour (`—` plus "No milestone matched — cannot check for MRs").
- **D-09 (user):** An MR whose title/branch carries **two keys that are both in this fix version** appears as a sub-line **under every matching task**. It is truthful (the MR really does serve both) and prevents a false "No merge request" on the second task. Consequence the planner must handle: the same MR's BR/MS cells exist in more than one place. They read the same query cache, so a fix fired in one location settles in both — but the per-`(mr.id, action)` sticky **error** state (P90 D-08) must be keyed such that this behaves sanely; a failure surfacing in one copy and not the other is a defect.

### Secondary table

- **D-10 (user):** The secondary table's MRs keep **fully working BR/MS fix cells** with identical P90 behaviour. Rationale: these are the MRs *most* likely to be drifted — an MR that reached the release branch with no Jira key is precisely the one needing a milestone — and read-only would be a functional regression against today's drift list, which acts on every row.
- **D-11 (user, satisfies criterion 5):** **Key shown + inline reason.** An out-of-scope-key MR shows its actual key in the key column with a warning glyph and a tooltip naming the problem (`TF-090 is not in fix version 33.7.0`). A keyless MR shows a plain muted `—`. One column carries both cases. Rejected: two labelled subgroups (too much chrome for a 2–3 row table), a dedicated reason column (breaks grid alignment, redundant with the key column).
- **D-12 (user):** The secondary table uses the **same column grid** as the primary — same span widths, straight vertical alignment through the gutter. In practice it should be the *same row renderer* as an MR sub-line with the key column repurposed, not a second parallel implementation.
- **D-13 (user):** When there are **no uncovered MRs, the entire section is hidden** — heading included. Its presence is the signal that something needs looking at; a permanent "nothing here" block is noise on every healthy release.

### Header, counts, banner, loading

- **D-14 (user):** The unified header carries **both** the Jira progress bar + `N / M done` badge (release readiness) **and** a flagged count (drift health). They answer different questions and each drove a section that is now gone; dropping either is a capability regression.
- **D-15 (user):** The flagged count is **distinct MRs with BR or MS flagged, across both tables**. A multi-key MR appearing under two tasks counts **once**; an MR flagged on both BR and MS counts **once**; secondary-table MRs **are** counted because they are actionable there (D-10). Reads as "this many merge requests need attention". Note this refines P89 D-13's per-row unit — rows are no longer unique per MR, so the count must dedupe by `mr.id`.
- **D-16 (user):** **One degraded banner**, above the primary table, stating the whole consequence: no GitLab milestone matched → only Jira-linked MRs found, branch and milestone checks cannot run, plus the existing "set a release date to enable milestone matching" hint when there is no date. Today's two banners (`IssuesSection`'s milestone warning and `drift-degraded-banner`) fire on the same condition and collapse into this one.
- **D-17 (user):** **Tasks render at Jira speed; MR sub-lines stream in.** As soon as the Jira query returns, task rows paint with a per-task `loading merge requests…` placeholder in the sub-line slot, replaced when the MR channels land. **Hard constraint:** the `⚠ No merge request` line (D-07) must **not** render while MR queries are pending — that would flash a false alarm on every task on every load. "Pending" and "resolved-empty" are distinct states and the renderer must distinguish them.

### Order

- **D-18 (from ROADMAP, satisfies criterion 6):** Primary-table rows keep **the order Jira returns** and never re-sort while the user acts. Because nothing re-sorts, the P89 D-11 `applyHeldOrder` / `orderRef` / `heldForVersion` freeze becomes **unnecessary and must be deleted, not carried over** — including its WR-09 per-release reset. The planner should treat leftover held-order code as a defect, not a safety net.

### Claude's Discretion

- Exact span widths for the shared grid, indent size, and the muted type scale for sub-lines.
- Section heading wording for the secondary table (something in the spirit of "Not covered by tasks above").
- Whether to render ARIA table/row/cell roles on the div+flex structure.
- Whether P89's channel-provenance tooltip on `!iid` (`Found via: Jira link, GitLab milestone…`) is retained — not discussed; retaining it is the conservative default.
- MR sub-line ordering within a single task — not discussed; a stable deterministic order (e.g. by `iid`) is the safe default. Must not re-sort on drift state.
- Where the flagged-count badge sits relative to the done badge in the header.

</decisions>

## Existing Code Insights

### Reusable Assets
- **`DriftActionCell` / `DriftMarkCell` (`MrDriftSection.tsx:113,149`)** — 28px `flex-none` cells with the complete pending/error/retry/inert state machine, live region, and focus handling. Move them into the new renderer as-is; do not reimplement.
- **`matchTicketKeyInTitle` + the linkification block (`MrDriftSection.tsx:93,441-475`)** — handles the normalised-vs-literal key problem (`extractTicketKeys` uppercases and rewrites `PROJ 123` → `PROJ-123`, so `indexOf` misses). Reuse verbatim for MR sub-line titles.
- **`statusPillClass` (`lib/statusStyles.ts`)** — for the task row's Jira status. Recorded caveat: its `min-w`/`text-center` collapse on a bare inline span; wrap in a flex div rather than adding geometry to the span.
- **`CachedAvatar`** — used by both sections today at `size={20}`; explicit px sizing is also the recorded fix for zero-width column collapse in this webview.
- **`Badge`** with the merged/opened/other colour ternary — identical in both files today; unify into one helper rather than copying the ternary a third time.

### Established Patterns
- **Presentational sections (P87 D-08):** the section fetches nothing and reads no store; every input including the whole `MrFixContext` arrives as props from `useReleaseDetail`. The new unified section must keep this.
- **Row-scoped hover groups:** P90 uses `group/row` + `group/fix` with `group-hover/row:` and `group-focus-visible/fix:` variants. D-05 means the `group/row` boundary moves to the MR sub-line.
- **Render-phase state adjustment guarded by a ref** (`DriftActionCell`'s `lastMarkRef`, `MrDriftSection`'s `heldForVersion`) — the project's chosen alternative to effects for prop-change reactions. React Compiler is on; `useMemo` is not a stability guarantee.
- **Overlay-button pattern for full-row click with a nested key button** — recorded project lesson; required by D-04.
- **div+flex rows over `<table>` for per-row sizing** — recorded project lesson; the direct basis for D-01.

### Integration Points
- `ReleaseDetailPage.tsx` renders `IssuesSection` then `MrDriftSection`; both call sites collapse to one component receiving both the Jira rows and the drift rows.
- `useReleaseDetail` already returns `matchedRows`, `wrongMilestoneByKey`, drift rows, `flaggedCount`, `hasMatchedMilestone`, and the fix context — the new attachment/partition derivation belongs alongside `buildIssueMrIndex`.
- Peek and full-open navigation (`onOpenIssue`, `onOpenIssueFull`, `onSeedBreadcrumb`) and `onNavigateToIssueFromMR` all survive and must be wired into the merged component.

### Gaps this phase must fill
- **No task↔MR attachment model exists.** Today `matchedRows` pairs an issue with at most **one** MR (`mr: GitLabMR | null`); the new shape needs `issue → GitLabMR[]` plus the partition of union MRs into covered / uncovered. This is the central new piece of logic.
- **`wrongMilestoneByKey` is a superseded heuristic.** `IssuesSection` uses it for its "Wrong milestone" cell; P89's channel model supersedes it. Determine whether it dies with `IssuesSection` — it should not survive into the new table as a parallel truth.
- **No pending-vs-empty distinction for MRs per task** (D-17's hard constraint).
- **No dedupe-by-`mr.id` count** (D-15) — `flaggedCount` is currently per drift row.
- **`applyHeldOrder` and its tests must be removed** (D-18), not left dormant.

<specifics>
## Specific Ideas

- The user picked the recommended option in every question, including the ones that cost more work (fix cells in the secondary table, streaming render, keeping both header metrics). The consistent thread is **do not regress capability that exists today** — every rejected alternative that was cheaper was cheaper by dropping something the current page does.
- The strongest stated principle, appearing twice (D-08 and D-17): **never assert a problem the app did not actually verify.** Both the degraded state and the loading state must be visually distinct from a confirmed "No merge request", not collapsed into it for simplicity.
- The user twice chose *not* to add summarising chrome — empty task-row gutter (D-06), hidden empty secondary table (D-13). Absence is the preferred signal for "nothing to see".

</specifics>
