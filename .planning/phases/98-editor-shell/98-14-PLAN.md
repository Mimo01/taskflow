<objective>
Close UAT gaps 1 (BLOCKER: Enter copies gap 0, so multi-paragraph saves fail) and 5 (MAJOR: an empty list item flashes the "Couldn't save safely" banner). Both are save problems in the editor/engine layer.

Purpose: any normal typing (paragraphs, new bullets) must save without false failures, and SAFE-05 must still hold: nothing is emitted that doesn't read back.
Output: schema keepOnSplit fix, a gap-keeper rule for new blocks, the pure `withoutEmptyListItems` transient rule used by `saveWiki`, and regression tests that drive the real Enter command.

Root cause (verified in node_modules/@tiptap/core/src/commands/splitBlock.ts): `keepOnSplit` only affects the at-end split, where the new node is built with `newAttributes`. A mid-block split (`types` undefined → `tr.split` copies the node and its attrs) and Enter at the start of a block copy `gap: 0` to both halves whatever `keepOnSplit` says. So `keepOnSplit: false` is needed but not sufficient. The gap-keeper must also give a new top-level block (index > 0, gap 0) gap 1. A blank line between top-level blocks always reads back as a block boundary, so gap 1 is always a safe spelling.

Gap 5 decision (planner's discretion, documented here): an empty list item has no wiki spelling (`* ` reads back as a paragraph), so it is a **transient** shape. `saveWiki` prunes empty list items (and lists left with no items) before the no-op check, the emit and `checkSaved`. The result is either 'unchanged' (no onChange, no banner) or 'saved' with the text of the pruned doc, which `checkSaved` has proven reads back as that pruned doc. This stays within SAFE-05: the emitted text always round-trips to the doc it describes, and the only content not carried is an empty bullet, which can't be written anyway. The editor doc keeps the empty item so the user can type into it.
</objective>
