<objective>
Close UAT gaps 2 (BLOCKER: the mode toggle doesn't move focus, so keystrokes edit the hidden rich doc) and 3 (MAJOR: programmatic focus leaves no working caret, and the first Cmd+Left is a no-op). Both are focus handling in WikiEditor.tsx, so they go in one plan.

Root cause (gap 2/3): `toRich` calls `editor.commands.focus()` synchronously, while `EditorContent` is still `className="hidden"` (display:none). React removes `hidden` only after the commit, so the focus targets an invisible element (TipTap focus also runs in rAF), and in WKWebView activeElement ends up on BODY. `toSource` moves no focus at all, and the hidden ProseMirror stays editable. The fix moves focus in a post-commit effect keyed on `mode`, makes the hidden editor non-editable, and binds Cmd+Left/Right explicitly, as Phase 96 SPIKE-FINDINGS recommended.

Cmd+Left/Right semantics (planner's decision, documented): bind `Meta-ArrowLeft` / `Meta-ArrowRight` (+ `Shift-Meta-…` to extend). Use explicit `Meta`, not `Mod`: on macOS it is Cmd, and on Windows/Linux `Mod` would be Ctrl, where Ctrl+Left is word-jump and must not be taken. The command moves to the **visual line** boundary: it measures with `coordsAtPos` + `posAtCoords` at the textblock's left/right edge on the caret's line, which matches native macOS behaviour in wrapped paragraphs. When layout can't be measured (zero rects, as in jsdom, or a throw), it falls back to the **logical line**: the nearest hardBreak before/after the caret, else the textblock start/end. The result is clamped to the textblock. It returns false (native handling) for non-text selections and non-textblock parents. LTR only (wiki text); this is noted in a comment.
</objective>
