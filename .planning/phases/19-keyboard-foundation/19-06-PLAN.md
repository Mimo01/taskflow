**Implementation in lib.rs:**

1. Add imports at the top:

```rust
use tauri::menu::{MenuBuilder, SubmenuBuilder, MenuItemBuilder};
```

2. Inside the `.setup(|app| { ... })` closure, after the stronghold plugin setup, build the menu:

```rust
// Build Help > Keyboard Shortcuts menu item
let shortcuts_item = MenuItemBuilder::new("Keyboard Shortcuts")
    .id("menu-keyboard-shortcuts")
    .accelerator("CmdOrCtrl+/")
    .build(app)?;

let help_menu = SubmenuBuilder::new(app, "Help")
    .item(&shortcuts_item)
    .build()?;

let menu = MenuBuilder::new(app)
    .item(&help_menu)
    .build()?;

app.set_menu(menu)?;
```

3. After `.setup()`, add the menu event handler using `.on_menu_event()`:

```rust
.on_menu_event(|app, event| {
    if event.id().as_ref() == "menu-keyboard-shortcuts" {
        // Emit event to frontend to open shortcuts panel
        let _ = app.emit("menu-keyboard-shortcuts", ());
    }
})
```

Place `.on_menu_event()` in the builder chain after `.setup()` and before `.invoke_handler()`.

**IMPORTANT:** The menu accelerator `"CmdOrCtrl+/"` is Tauri's cross-platform format — it becomes Cmd+/ on macOS and Ctrl+/ on Windows/Linux. This is just a display label in the menu; the actual keyboard handling is done by react-hotkeys-hook in the frontend. If you find that the accelerator also triggers and conflicts with the frontend handler, that is fine — both paths (native accelerator and react-hotkeys-hook) should open the same panel. But if double-fire occurs, remove the accelerator from the menu item and keep it display-only.

**Cargo.toml check:** If compilation fails with unresolved imports for `tauri::menu::*`, add the `"menu"` feature:
```toml

```

Do NOT add a separate `tauri-plugin-menu` crate — the menu API is part of the core `tauri` crate in v2.
