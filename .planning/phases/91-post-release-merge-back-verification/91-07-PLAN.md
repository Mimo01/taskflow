<objective>
Close the service-and-resolver half of 91-VERIFICATION's single remaining gap
(truth 5): the tag evidence channel is the only one of four with neither an
in-flight signal nor a failure signal reaching `resolveMergeBackVerdict`.

Two root causes live in this plan's files. First, `searchProjectTags`
(`gitlab.ts:352-385`) swallows every transport/auth/non-ok error in
`catch { return allTags }` (L380-382), so no caller can ever tell a 500 from
"no matching tag". Second, `resolveMergeBackVerdict`'s parameter surface
(`mergeBackVerification.ts:104-116`) and step 5 (L203-211) treat
`tagName === null` identically whether the tag query is in flight, resolved to
genuinely nothing, or failed.

The fix must be *symmetric* with the three channel guards this same phase
already shipped — `defaultBranchCheckFailed` (step 2, L145-150),
`trackingMRsUnavailable`/`trackingMRsCheckFailed` (step 3, L152-163), and
`compareCheckFailed` (steps 6-7, L213-221). This is not a new invention; it is
the fourth instance of an established in-file pattern.

This plan also closes 91-REVIEW WR-01 (step 10 checks `trackingMRsCheckFailed`
but not `trackingMRsUnavailable` before emitting `likely-not-merged`).

Purpose: without an observable failure and a resolver branch to receive it, the
hook wiring in 91-08 has nothing to wire.
Output: a fail-closed tag fetcher and a resolver whose fourth channel degrades
as safely as the other three, both unit-tested.
</objective>
