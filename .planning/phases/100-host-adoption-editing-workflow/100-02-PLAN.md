<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| app → local disk (drafts.json) | Draft text is written in plaintext to the app data dir |
| disk → app (restore) | A stored draft is read back and later fed to the editor |
| Jira account A → account B | Same machine, different Jira identity |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-100-04 | Information Disclosure | drafts.json plaintext | accept | Same exposure class as notifications.json/settings.json in the app data dir (OS user-scoped); drafts are never logged, never sent to the debug-log store, and are deleted on save/discard |
| T-100-05 | Information Disclosure | cross-account leakage | mitigate | reconcileOwner clears all drafts when base URL + username differ (D-21), wired in ConnectionsSection Jira onConnected and the app-level useDraftsAccountGuard |
| T-100-06 | Tampering | restored draft as untrusted input | mitigate | The store holds plain strings only; hosts pass them as `value` into WikiEditor, which parses through loadWiki/the schema (no dangerouslySetInnerHTML). A malformed persisted entry (non-string text) is dropped by setDraft/selector type checks |
| T-100-07 | Denial of Service | hydration race deleting drafts | mitigate | No writes before hydration (tested), so an empty mount never overwrites a stored draft |
</threat_model>
