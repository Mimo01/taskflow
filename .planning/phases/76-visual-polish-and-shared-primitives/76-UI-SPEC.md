### Priority Stripe Color Contract

The stripe is a non-text graphical object. WCAG threshold is **3:1** against `bg-card` in both themes (WCAG 2.1 §1.4.11 Non-text Contrast).

**Ramp intent (locked — D-01/D-02 from CONTEXT.md):**

| Priority | Intent | Light mode constraint | Dark mode constraint |
|----------|--------|----------------------|---------------------|
| Highest | Saturated red | Must achieve ≥ 3:1 vs `oklch(1 0 0)` | Must achieve ≥ 3:1 vs `oklch(0.205 0 0)` |
| High | Saturated orange | Must achieve ≥ 3:1 vs light `bg-card` | Must achieve ≥ 3:1 vs dark `bg-card` |
| Medium | Saturated yellow | Must achieve ≥ 3:1 vs light `bg-card` | Must achieve ≥ 3:1 vs dark `bg-card` |
| Low | Gray (faded) | Must achieve ≥ 3:1 vs light `bg-card` | Must achieve ≥ 3:1 vs dark `bg-card` |
| Lowest | Lighter gray (more faded) | Must achieve ≥ 3:1 vs light `bg-card` | Must achieve ≥ 3:1 vs dark `bg-card` |
| Unset / unmapped | Neutral gray | Must achieve ≥ 3:1 vs light `bg-card` | Must achieve ≥ 3:1 vs dark `bg-card` |

**Executor shade selection guidance:**

Light mode `bg-card` is effectively white. To clear 3:1 against white, any Tailwind color shade must have relative luminance ≤ ~0.31. This rules out all `*-100`, `*-200`, and `*-300` shades. Starting point: `*-500` for saturated colors, `gray-600` / `gray-500` for the gray tones.

Dark mode `bg-card` is `oklch(0.205 0 0)` (~#2a2a2a). Against this dark surface, lighter shades clear 3:1 more easily. Light/dark variants must use different shades — do NOT use the same Tailwind shade class for both modes.

**Tailwind class structure (follow `statusStyles.ts` / `epicColors.ts` pattern):**

```ts
// lib/issueDisplayUtils.ts — priorityStripeClass()
// Pattern: raw class for light, dark: prefix for dark variant
const PRIORITY_STRIPE: Record<string, string> = {
  Highest: 'border-l-red-600 dark:border-l-red-400',
  High:    'border-l-orange-600 dark:border-l-orange-400',
  Medium:  'border-l-yellow-500 dark:border-l-yellow-300',
  Low:     'border-l-gray-500 dark:border-l-gray-400',
  Lowest:  'border-l-gray-400 dark:border-l-gray-500',
};
const DEFAULT_STRIPE = 'border-l-gray-400 dark:border-l-gray-500';
```

Note: The shade numbers above are starting-point recommendations. Executor MUST verify contrast ratio for each shade against actual `bg-card` tokens before shipping. The shades may be adjusted ±1-2 stops to meet 3:1 while preserving the ramp intent. If `yellow-500` in light mode does not clear 3:1, move to `yellow-600`. Do not compromise the ramp intent — preserve the red > orange > yellow > gray hierarchy.

**Stripe mechanics (D-04 from CONTEXT.md):**

The stripe uses the `border-l-{N}` Tailwind mechanism already present on `TaskCard` outer button. Apply `border-l-4` + the priority stripe color class to the card's outer `<button>` element. The stripe replaces the existing `border-l-2 border-l-muted` subtask marker when a priority class is present; for non-subtask cards, `border-l-4` + priority color is the full left-border treatment.

## Done-State Strike Treatment

Source: D-05, D-06, D-07 from CONTEXT.md; `TaskCard.tsx` lines 112-120.

### Rule

Apply `line-through` to the **issue key element only** (`<span>` or equivalent containing the monospace key string). The summary text is NOT struck through in any view.

### Canonical Implementation (from TaskCard.tsx line 114)

```tsx
<span
  className={cn(
    'text-xs font-mono text-muted-foreground',
    issue.fields.status.statusCategory?.key === 'done'
      ? 'line-through group-hover:[text-decoration-line:underline_line-through]'
      : 'group-hover:underline',
  )}
>
  {issue.key}
</span>
```

### `isDoneStatus` contract

```ts
// lib/issueDisplayUtils.ts
export function isDoneStatus(statusCategory: { key: string } | null | undefined): boolean {
  return statusCategory?.key === 'done';
}
```

Uses `statusCategory.key === 'done'` — NOT a status-name match. Handles all custom done-statuses automatically. Mirrors existing kanban behavior.

### `doneSummaryClass` contract

Despite its name, this function returns the class for the **issue key** element, not the summary. It returns `line-through` when done, empty string otherwise. The name is kept as mandated by the roadmap export contract.

```ts
// lib/issueDisplayUtils.ts
export function doneSummaryClass(statusCategory: { key: string } | null | undefined): string {
  return isDoneStatus(statusCategory) ? 'line-through' : '';
}
```

### Hover treatment

On cards (interactive contexts), the key element should receive `group-hover:[text-decoration-line:underline_line-through]` to show both underline and strike simultaneously on hover — identical to `TaskCard.tsx`. On non-interactive list rows (Backlog list, Standup Today), this hover decoration is optional; apply if the row has a click/hover handler, omit if purely static.

### Application surfaces

| Surface | Element to strike | Component |
|---------|------------------|-----------|
| Sprint board card | Issue key `<span>` | `TaskCard.tsx` (refactor to use shared `isDoneStatus` / `doneSummaryClass`) |
| Backlog active-sprint list | Issue key `<span>` | `BacklogRow.tsx` |
| Standup Notes Today section | Issue key `<span>` | `TodayColumn.tsx` (`TodayInProgressSection` / `TodayUpNextSection`) |
| Dashboard per-story list | Issue key `<span>` | Where rendered; VISUAL-03 satisfied if no per-story rows exist (aggregate-only) |

## `priorityStripeClass` contract

```ts
// lib/issueDisplayUtils.ts
export function priorityStripeClass(priorityName: string | null | undefined): string {
  return PRIORITY_STRIPE[priorityName ?? ''] ?? DEFAULT_STRIPE;
}
```

Returns a `border-l-*` color class. The caller is responsible for adding `border-l-4` (width) to the element — `priorityStripeClass` returns color only, not width, to keep concerns separated and let callers compose.

Usage at call site:

```tsx
<button
  className={cn(
    'border rounded-lg ... border-l-4',
    priorityStripeClass(issue.fields.priority?.name),
    // ... rest of existing classes
  )}
>
```
