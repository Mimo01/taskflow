| persisted Zustand store → in-memory state | Pre-v19 persisted settings (with stale `dashboardLayout` key) cross into the new v19 store shape via the `migrate` function. |
| developer filesystem → build artifact | File deletions cross from source tree into bundled output. A leaked import would surface as a build error. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-59-01 | Tampering | settings.store.ts v19 migration | mitigate | Migration is additive-only and bumps version; extra persisted keys are dropped implicitly by Zustand LazyStore. v9 migration is patched to stop writing `dashboardLayout`, so re-running v9→v19 on a legacy store does not resurrect the deleted field. |
| T-59-02 | Denial of Service | atomic deletion ordering (D-04) | mitigate | All registry-related deletions + store import removal happen in Task 1 of this plan as one edit set; CI never observes a half-deleted state. |
| T-59-03 | Information Disclosure | persisted user settings | accept | The `dashboardLayout` payload contains no PII — only widget IDs, positions, and JQL strings the user chose; dropping it discards user customisation but exposes nothing. |
| T-59-04 | Repudiation | git history of deletion | accept | Git commit log preserves the deletion event with full file content; standard repo audit suffices. |
| T-59-05 | Spoofing | none — no auth surface | accept | This plan does not touch authentication, network calls, or user identity. |
| T-59-SC | Tampering | npm/pip/cargo installs | mitigate | No package installs in this plan; package removal happens in Plan 03 with its own audit. |
