<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client drag UI → Jira transition endpoint | A drop selects a `transitionId` and calls `postTransition` (already-authenticated Bearer PAT); Jira server is the authority that executes/validates the workflow transition |
| pointer event → optimistic local state | A drop optimistically mutates `localIssues` before the server confirms; rollback restores the snapshot on failure |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-79-01 | Elevation of Privilege | drop → `postTransition` | mitigate | The drop's `transitionId` is selected only from the server workflow envelope via the dropModel (Plan 02), never user free-text; Jira re-validates the transition on `postTransition` and a forbidden/failed call rolls back (TRAN-04). No client-side privilege decision is made. |
| T-79-02 | Tampering | drop targets exclude screen/validator transitions | mitigate | Drop zones are built from `filterDroppableTransitions` (Plan 02) which excludes `hasScreen`/`hasValidators` (D-07); such transitions are never drop targets, so they cannot be silently fired by drag — they require the full StatusPopover/screen flow. |
| T-79-04 | Denial of Service (self) | optimistic state + rollback | accept | A failed transition rolls back local state and surfaces an inline error; no retry storm (single drop = single call). Low risk, internal single-user tool. |
| T-79-SC | Tampering | npm/pip/cargo installs | accept | Zero packages installed this phase (RESEARCH Package Legitimacy Audit — all dnd-kit/TanStack deps already present). No supply-chain surface. |
</threat_model>
