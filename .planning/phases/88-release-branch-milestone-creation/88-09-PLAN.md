<objective>
Close CR-02 (blocker, RELMS-02) and the wiring half of CR-03 (blocker, RELBR-04), plus WR-10.

CR-02: `createMilestoneMutation.onSuccess` invalidates only the detail page's windowed milestone
key `['gitlab-milestones', activeGitlabProject, milestoneWindow?.from, milestoneWindow?.to]`.
`ReleasesTab` caches the same prefix under a *different* window (min..max of all fix version
dates ±7d), and TanStack Query matches by prefix — the detail window array is not a prefix of the
list window array, so the list's entry is never invalidated and keeps showing "No GitLab link"
plus the missing-milestone triangle for up to the 5-minute `staleTime`. The sibling
`createBranchMutation` already invalidates at project granularity; match that pattern.

CR-03 wiring: the `gitlab-branch` query discards `isError`, so a 401/403/500/timeout collapses
into `{ kind: 'loading' }` and the Create-branch button (gated on `kind === 'missing'`) becomes
unreachable with no error copy and no retry. Plan 88-08 added the `'check-failed'` state and the
`branchCheckFailed` parameter; this plan feeds them and renders the result.

WR-10: both mutations substitute `activeGitlabProject ?? 0` rather than blocking, so a POST to
`/api/v4/projects/0/...` is reachable. The read queries are already guarded by
`enabled: !!activeGitlabProject`; the mutations are not.

Purpose: a confirmed write must be visible everywhere the phase promised it, and a failed check
must be recoverable rather than a dead end.
Output: guarded, correctly-invalidating mutations; a `check-failed` sidebar row with retry; the
phase's first `useReleaseDetail` test file.
</objective>
