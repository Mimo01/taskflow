<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| user click → GitLab write | A confirmed user action triggers the app's second-ever GitLab write operation |
| derived branch name → POST body | The derived name and the fetched default branch are sent as the `branch`/`ref` fields |
| GitLab error body → dialog render | Server rejection text is rendered back verbatim |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-88-V5 | Tampering | Create-button gating in `ReleaseDetailSidebar.tsx` | mitigate | ASVS V5 defense-in-depth: `resolveBranchState` returns `invalid-ref` for any name failing `isValidGitRefName`, and that state renders the Create button `disabled` — an invalid git ref has no reachable write path from the UI. GitLab's server-side validation remains the authority (D-08). |
| T-88-INJ | Tampering | `createBranch` request body | mitigate | `branch` and `ref` travel in the `JSON.stringify` body, not a URL path segment, so no encoding ambiguity exists. The derived name is constrained to `release/` + a `\d+\.\d+\.\d+` capture. |
| T-88-CSRF-ANALOG | Spoofing | Unintended write from a stray click | mitigate | The write is behind a blocking confirm dialog naming both the branch and the ref (RELBR-04). No write fires from the row button itself. |
| T-88-AUTH | Elevation of Privilege | 403 on branch creation (protected-branch rule or insufficient role) | accept | Permission/role gating is explicitly out of scope (team is all Developer+). A 403 surfaces as a normal `ApiError` and, per D-16, renders inside the dialog for the user to act on. No client-side pre-authorization is attempted. |
| T-88-ERR | Information Disclosure | GitLab error body rendered verbatim in the dialog | accept | The message concerns a resource the PAT holder is already authorized for; verbatim surfacing is a deliberate requirement (D-16) and discloses nothing beyond existing authorization. |
| T-88-ID | Information Disclosure | PAT during the write | transfer | The write goes through `apiFetch('gitlab', ...)`; `PRIVATE-TOKEN` redaction is already handled in `apiFetch.ts:85`. |
| T-88-SC | Tampering | npm installs | accept | Zero packages installed by this plan (88-RESEARCH.md § Package Legitimacy Audit: not applicable). No legitimacy checkpoint required. |
</threat_model>
