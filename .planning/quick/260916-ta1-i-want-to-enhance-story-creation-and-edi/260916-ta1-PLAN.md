Contracts that exist today and must be used as-is:

- `uploadAttachment(baseUrl: string, token: string, issueKey: string, file: File): Promise<JiraAttachment[]>` — `@/services/jira/attachments`. Hard-requires a real issue key in the URL path; there is no create-time attachment endpoint.
- `attachmentRef(att: JiraAttachment): string` — `@/lib/attachment-markup`. Image → `!filename!`, non-image → `[^filename]`, hazardous filename → resolved-URL fallback forms.
- `isImageAttachment(att: Pick<JiraAttachment, 'mimeType'>): boolean` — same module.
- `AttachmentPickerModal` props: `{ open, onOpenChange, attachments, onSelect }` — issue-key agnostic, reusable verbatim.
- `WikiRenderer` accepts `attachments?: Record<string, string>` (filename → content URL); `DescriptionEditor` currently omits it.
- `readSecret('jira-pat')` — `@/services/stronghold`.
- `createIssue(...)` returns `{ key, ... }`; `useIssueMutations.createMutation.mutationFn` already awaits it at `useIssueMutations.ts:100`.

New contracts introduced by this plan (define in Task 1, consume in Task 2):

- `DescriptionEditorProps` gains: `attachments?: JiraAttachment[]`, `stagedFiles?: File[]`, `onFileSelected?: (file: File) => void`, `onRemoveStagedFile?: (index: number) => void`, `uploadingName?: string | null`, `uploadError?: string | null`.
- `EditInitialValues` gains optional `attachments?: JiraAttachment[]`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| User filesystem → app | Arbitrary user-chosen files enter via paste/drop/file-input |
| App → Jira REST API | Multipart upload with a PAT bearer token, plus issue create/update writes |
| Jira attachment filename → wiki markup string | Attacker-influenced filename is embedded in markup that WikiRenderer later parses |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-ta1-01 | Tampering | `stagedAttachmentRef` / `attachmentRef` in `attachment-markup.ts` | mitigate | Global-strip `!`, `|`, `]` from filenames before embedding in `!…!` / `[^…]` so a crafted filename cannot break out of the markup delimiters and inject arbitrary wiki markup (same hazard class already handled in `attachmentRef`) |
| T-ta1-02 | Information disclosure | `readSecret('jira-pat')` in the new upload mutation | mitigate | Read the PAT at mutation time and pass it only to `uploadAttachment`; never place it in component state, props, or error strings (error text names the file only) |
| T-ta1-03 | Denial of service | Staged file list in create mode | accept | Staged `File[]` are user-chosen local handles held only until submit and cleared on modal reopen; Jira enforces its own upload size limit and returns an error the existing `ApiError` path surfaces |
| T-ta1-04 | Repudiation | Post-create upload loop in `useIssueMutations` | mitigate | Per-file failures are collected and surfaced by filename to the user rather than swallowed, so a partially-attached issue is never silently reported as fully successful |
| T-ta1-SC | Tampering | npm/pip/cargo installs | mitigate | No new packages introduced — `lucide-react`, `@tanstack/react-query`, and all touched modules are existing dependencies; no package-manager install task exists in this plan, so no legitimacy gate is required |
</threat_model>
