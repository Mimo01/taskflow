# Phase 261013-l97: Code Review Report

**Reviewed:** 2026-10-13
**Depth:** quick (manual read of the five source files; test files not reviewed)
**Status:** issues_found

## Summary

The aggregation helpers (`aggregateCycleScope`, `matchesCycleFilter`, UTC-based day math) are consistent with each other. Overdue, due-soon, week and later buckets use the same boundary rules in the aggregator and the list filter. The main risk is the virtualizer wiring against the page-owned scroll element, which depends on ref-attachment order. There are also a few date and a11y defects.

## Critical Issues

### CR-01: Virtualizer scroll element and offset are not set up on mount when the cached list renders immediately

**File:** `taskflow/src/routes/dashboard/AioCycleList.tsx:285-309`
**Issue:** `getScrollEl` returns `scrollElementRef.current`, and that ref points at `paneRef`. `paneRef` is attached to a parent `<div>` in `AioProjectOverviewPage`. React attaches refs during the layout phase, children before parents. On first mount the list's `useLayoutEffect` therefore runs while `paneRef.current === null`, for two reasons:
- `measureOffset` returns early, so `rowsOffset` stays 0.
- The `ResizeObserver` is never created, because `scrollEl` is null and the effect returns.

The effect only reruns when `virtualize`, `isLoading`, `isPending` or `visible.length` changes. This is fine on a cold load, where `isPending` flips. It breaks when the data is already in the react-query cache. That happens when the user returns to the page, or the folder switches to a cached one, and the list mounts with `virtualize` already true and no later dep change.

In that case `scrollMargin` is 0 while the rows actually start below the KPI tiles and charts, roughly 400px or more. The visible window is then computed against the wrong offset, so rows at the top of the viewport go missing or are blank. Nothing re-measures the offset when the dashboard above changes height.

**Fix:** Do not rely on the parent ref being set during the child's layout effect. Either:
- Pass the scroll element as state: `const [paneEl, setPaneEl] = useState<HTMLElement|null>(null)` with `ref={setPaneEl}` in the page, and pass `paneEl` down so the effect depends on it; or
- Have the effect depend on a `scrollEl` value, and run `measureOffset` plus the observer setup in a `useEffect` that is guaranteed to run after refs attach.

Also observe the rows container, or `rowsRef.current.previousElementSibling`, instead of relying on `firstElementChild`.

## Warnings

### WR-01: `toDateKey` mixes UTC/offset-local and browser-local semantics

**File:** `taskflow/src/lib/aio-cycle-list.ts:16-27`
**Issue:** Numeric epoch-ms values are converted with the browser's local date (`toLocalDateString`). ISO strings take the literal `YYYY-MM-DD` prefix, which is the date in the string's own offset or in UTC for `Z`. For example, `2026-10-13T23:30:00Z` yields the 13th for a string and the 14th for the equivalent number in UTC+2. `today` is browser-local. Overdue, due-soon and week bucketing can therefore be off by one day around midnight, and the two input shapes disagree with each other. The regex also accepts impossible dates such as `2026-13-45`.
**Fix:** For strings with a time component, parse with `new Date(raw)` and use `toLocalDateString`. Keep the prefix shortcut only for date-only strings (`/^\d{4}-\d{2}-\d{2}$/`), and validate the month and day ranges.

### WR-02: `today` is computed per render and can go stale or churn

**File:** `taskflow/src/routes/dashboard/AioProjectOverviewPage.tsx:97`
**Issue:** `toLocalDateString(new Date())` is only re-evaluated when the page re-renders. A session left open across midnight keeps stale overdue and week buckets until some other state change. When it does flip, `scope` and `visible` recompute. A stored `endWeek` or `dueSoon` filter silently changes meaning. There is no timer.
**Fix:** Hold `today` in state refreshed by a timeout to the next local midnight (or on `visibilitychange`). Optionally clear the cross-filter when `today` changes.

### WR-03: The scope bar shows "0 open · 0 closed" while loading or on error

**File:** `taskflow/src/routes/dashboard/AioProjectOverviewPage.tsx:333-338`
**Issue:** `scope` is aggregated over `[]` while the cycles load or fail, so `openCount` and `closedCount` render as literal zeros. The tiles are skeletons in that state, but the bar is not, so it shows false data. On error the dashboard is hidden but the bar still reports zeros.
**Fix:** Pass `openCount={loaded ? scope.openCount : undefined}` and render a skeleton or nothing for the counts until the data is present.

### WR-04: The Pass rate tile is a focusable no-op button, and `aria-pressed` is not set for non-filter tiles

**File:** `taskflow/src/routes/dashboard/AioCyclesDashboard.tsx:95-106`
**Issue:** `Tile` always renders a `type="button"` trigger. The Pass rate tile has no `onClick`, so it is a tab stop that does nothing. Screen readers announce it as an actionable button. The `cursor-default` styling only covers the mouse.
**Fix:** When `onClick` is absent, render the trigger as a non-button, with `render={<div tabIndex={0} />}` only if the tooltip must stay keyboard reachable, and drop the button role. Alternatively, make the Pass rate tile filter by status.

### WR-05: Cross-filter is not reset when the Open|All control changes

**File:** `taskflow/src/routes/dashboard/AioProjectOverviewPage.tsx:331-337`, `taskflow/src/routes/dashboard/AioCyclesScopeBar.tsx:43-46`
**Issue:** `AioCyclesScopeBar` exposes `onStatusChange`, but the page does not pass it. `onShowOpen` clears the filter, so the two paths behave differently. Switching Open to All with an `owner` or `status` filter active keeps the filter, but the owner and execution charts are recomputed under the new scope. The owner row that was highlighted can disappear because it fell out of the top 6, while the chip and the filtered list persist. The user then has no highlighted row to toggle off, and can only clear the filter through the chip.
**Fix:** Pass `onStatusChange={() => setCycleFilter(null)}`, or at least clear owner and status filters on scope change.

### WR-06: The tooltip trigger also gives the row buttons an `aria-label` that hides their content

**File:** `taskflow/src/routes/dashboard/AioCyclesDashboard.tsx:356-362`
**Issue:** The schedule column's `aria-label` (`"Oct 13 – Oct 19: 3 cycles"`) overrides the visible week and month text. That is acceptable. However the Overdue and Later buckets announce "Overdue: 0 cycles" even when empty and still focusable, giving up to 10 tab stops with no data. Zero-count buckets are also clickable and produce an "No cycles match" state.
**Fix:** Disable (`disabled` or `aria-disabled`) buckets with `count === 0`, and skip them in the tab order.

## Info

### IN-01: Duplicate constants

**File:** `taskflow/src/routes/dashboard/AioCyclesDashboard.tsx:31-34`
**Issue:** `TILE_BUTTON_CLASS` and `ROW_BUTTON_CLASS` are identical strings.
**Fix:** Merge into one constant.

### IN-02: `hasDates` and `hasEffort` are recomputed on every render over all visible rows

**File:** `taskflow/src/routes/dashboard/AioCycleList.tsx:266-273`
**Issue:** Both run `visible.some(...)` unmemoized on each render. With ~1,300 cycles and the scroll-driven virtualizer re-renders, this repeats the work for every scroll tick. It is also unmemoized relative to `visible`. The visible column set can change as the cross-filter changes, shifting the layout. `ProgressCell` additionally rebuilds the status lookup for every row, because `cycleProgress` is called without the shared lookup. This is a performance note only, outside v1 scope.
**Fix:** Wrap in `useMemo` keyed on `[visible, summaryByID]`, and reuse `progressByID` in `ProgressCell`.
