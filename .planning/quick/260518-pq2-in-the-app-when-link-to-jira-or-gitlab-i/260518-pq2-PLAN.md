<objective>
When a Jira or GitLab URL is rendered as a clickable link inside the app (issue descriptions, comments, anywhere WikiRenderer is used), clicking it should first try to navigate to the equivalent in-app detail page. Only when no internal mapping is possible should the link fall back to opening the OS browser via `openUrl`.

Purpose: Today, every rendered link inside Wiki content goes through `openUrl(href)` (WikiRenderer.tsx:651), which always hijacks to the OS browser even when the destination is a Jira issue or GitLab MR the app already renders natively. This breaks flow — the user wants to stay in the app for things the app can show.

Output:
- New pure helper `tryInternalPath()` (with tests) that maps known external URLs → internal React Router paths
- WikiRenderer anchor handler updated to consult the helper first, then fall back to `openUrl`
</objective>

  <behavior>
    Helper signature (pure function, no React, no auth-store import — receives all state via ctx so it is trivially unit-testable):

      type InternalLinkCtx = {
        jiraBaseUrl: string | null;
        gitlabBaseUrl: string | null;
        activeGitlabProject: number | null;
        activeGitlabProjectPath: string | null;
      };
      export function tryInternalPath(href: string, ctx: InternalLinkCtx): string | null;

    Returns the internal React Router path on a hit (e.g. "/issue/PROJ-12345"), or null on a miss.

    Test cases (vitest):
    - Jira browse hit:
        href = "https://jira.example.com/browse/PROJ-12345"
        ctx.jiraBaseUrl = "https://jira.example.com"
        → "/issue/PROJ-12345"
    - Jira browse hit with trailing slash on jiraBaseUrl ("https://jira.example.com/") → still "/issue/PROJ-12345"
    - Jira browse hit with trailing slash on href ("…/browse/PROJ-1/") → "/issue/PROJ-1"
    - Jira browse hit with query string ("…/browse/PROJ-1?foo=bar") → "/issue/PROJ-1" (query stripped)
    - Jira browse miss — wrong host: href on different jira host than jiraBaseUrl → null (do NOT silently match other Jira instances; the app only knows credentials for the configured host)
    - Jira non-browse URL ("https://jira.example.com/secure/attachment/123/file.png") → null
    - Jira URL with no jiraBaseUrl configured (ctx.jiraBaseUrl = null) → null
    - GitLab MR hit (path matches active project, path form "group/repo"):
        href = "https://gitlab.example.com/group/repo/-/merge_requests/42"
        ctx.gitlabBaseUrl = "https://gitlab.example.com"
        ctx.activeGitlabProject = 99
        ctx.activeGitlabProjectPath = "group/repo"
        → "/mr/99/42"
    - GitLab MR hit (path matches active project, path form "Org / My Project" — the auth store sometimes stores a display label with spaces; normalize by lowercasing + stripping spaces around slashes before comparing):
        href = "https://gitlab.example.com/org/my-project/-/merge_requests/7"
        ctx.activeGitlabProjectPath = "Org / My Project"
        ctx.activeGitlabProject = 12
        → "/mr/12/7" — IF the normalized comparison can match "org/my-project" vs "org/my project". If the spec is ambiguous prefer the safer rule: match only when the URL path (slash-segments before "/-/merge_requests/") equals the trimmed activeGitlabProjectPath after lowercasing and trimming whitespace around slashes. If they don't match after normalization → null.
    - GitLab MR miss — different group/project than activeGitlabProjectPath: href = "https://gitlab.example.com/other/repo/-/merge_requests/1", ctx.activeGitlabProjectPath = "group/repo" → null (the numeric id we have is for the wrong project; safer to fall back to openUrl than to navigate to the wrong MR)
    - GitLab MR miss — gitlabBaseUrl mismatch → null
    - GitLab MR miss — activeGitlabProject is null → null (no numeric id to construct internal route)
    - GitLab MR miss — gitlabBaseUrl not configured → null
    - GitLab non-MR URL (e.g. "/group/repo/-/issues/5", "/group/repo/-/pipelines/9") → null
    - Empty href "" → null
    - href with only whitespace → null
    - href that is not a URL ("javascript:alert(1)") → null (do not even attempt to parse)
    - href that throws in `new URL()` (malformed) → null (helper must not throw)
  </behavior>

Do NOT navigate to the active-project route for a different project's MR (would be a correctness bug).
