## Summary

This change extracts a shared `assignee-filter.ts` module with a reserved
`UNASSIGNED_FILTER` sentinel and routes both the Backlog and Sprint Board
assignee predicates through a single `matchesAssigneeFilter` helper. The
refactor is clean and the four focus invariants hold:

- **OR semantics:** Correct. The sentinel branch (`assignee == null`) returns
  `true` early, and the named pass returns `true` on the first substring hit;
  the two are unioned. Verified by the `OR semantics` test.
- **Sentinel only when unassigned visible:** Correct. `buildAssigneeOptions`
  only prepends the sentinel when `hasUnassigned` is set.
- **Two predicates identical:** Correct. Both views now delegate to the same
  helper; the old inline IIFEs are gone.
- **Sentinel never collides with a real assignee:** Mostly correct, with one
  residual edge case (WR-01) the code's own JSDoc flags as threat T-s09-01.

11 unit tests pass. `displayMap` on `FilterDropdown` already existed and is
used correctly for chip + dropdown rendering. The `JiraIssue[]` typing on both
`allIssues` (Backlog) and `localIssues` (Sprint Board) makes the helper calls
type-safe. No critical issues found.

## Warnings

### WR-01: Sentinel can be shadowed by a real assignee literally named `__unassigned__`

**File:** `taskflow/src/lib/assignee-filter.ts:38-69`
**Issue:** If a real user's `displayName` is exactly `__unassigned__`,
`buildAssigneeOptions` adds it to the `named` set and surfaces it as a normal
option. When the user selects it, `matchesAssigneeFilter` sees
`activeAssignees.has(UNASSIGNED_FILTER)` is true and matches **all unassigned
issues** via the sentinel branch — not the user. Conversely, issues genuinely
assigned to that user are matched only by the substring pass, so the two
populations silently merge. The module JSDoc acknowledges this as threat
T-s09-01 ("Chosen to be unlikely to collide") but does not actually defend
against it — improbability is the only mitigation.
**Fix:** Defensively exclude the sentinel literal from the named-options pass so
the two paths can never both be active for one value:
```ts
} else if (assignee.displayName && assignee.displayName !== UNASSIGNED_FILTER) {
  named.add(assignee.displayName);
}
```
Optionally pick a more collision-proof sentinel (e.g. a value containing a NUL
or zero-width char) since `__unassigned__` is a plausible bot/system handle.

## Info

### IN-01: JSDoc says `=== null` but code uses `== null`

**File:** `taskflow/src/lib/assignee-filter.ts:21, 60, 65`
**Issue:** The header comment and the threat note state the sentinel is "matched
STRICTLY against `issue.fields.assignee === null`", but the implementation uses
loose `== null` (matching both `null` and `undefined`). The looser check is
arguably safer for real Jira payloads, but the doc/code mismatch is misleading
for the next maintainer reasoning about the "strict" guarantee.
**Fix:** Align the comments with the actual `== null` semantics (or tighten the
code to `=== null` if undefined-assignee is truly impossible per the
`JiraIssue` type, where `assignee` is `{...} | null`).

### IN-02: Empty-string query in the active set would match every issue

**File:** `taskflow/src/lib/assignee-filter.ts:66-67`
**Issue:** If `activeAssignees` ever contained `''`, `name.includes('')` is
always `true`, so every issue (including assigned ones) would pass. This is
pre-existing behavior carried over verbatim from both inline predicates, not
introduced here, and no current call path adds `''` to the set — flagging only
so the shared helper documents/guards the invariant in one place.
**Fix:** Skip blank queries in the loop: `if (!q) continue;` alongside the
existing `if (q === UNASSIGNED_FILTER) continue;`.
