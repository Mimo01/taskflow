The existing `fetchAssignableUsers` is a SEARCH (multi-result, project-scoped) — wrong tool. A direct GET-by-username function fills the gap.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Client → Jira DC REST API | PAT in Authorization header crosses this boundary on every call |
| Untrusted AIO ownedByID string → Jira user lookup URL | A malicious or malformed ownedByID could attempt URL injection |
| Jira response JSON → typed JiraAssignableUser | Response shape trusted via TypeScript cast (no runtime validation) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-57-03-01 | T (Tampering) | URL construction with username param | mitigate | `encodeURIComponent(username)` applied to the user-supplied string prevents `&`, `?`, `=`, `..`, and other characters from breaking out of the query param. Acceptance criteria require encodeURIComponent usage. |
| T-57-03-02 | I (Information Disclosure) | PAT leakage in URL or error | mitigate | PAT travels only in `Authorization: Bearer` header (via apiFetch). The new function follows the existing fetchAssignableUsers contract — token never appears in URL or error message. |
| T-57-03-03 | D (Denial of Service) | N-many parallel user lookups from large folder | mitigate | The new function itself is single-call. DOS-vector lives in Plan 04 (component) — that plan must dedupe unique ownedByIDs before spawning `useQuery` calls (D-07). Outside this plan's scope; Plan 04's component test verifies dedup. |
| T-57-03-04 | R (Repudiation) | User lookup failures silently null | accept | On any non-2xx (including 401), the function returns `null`. This is intentional (D-08) — the UI must remain functional even when Jira partially fails. Trade-off: silent 401s could mask an expired PAT. Mitigation: other queries on the page (cycle list, folder tree) will surface the 401 via their throw → ErrorState. Accept residual risk. |
| T-57-03-05 | E (Elevation of Privilege) | Returned user object treated as authoritative for owner display | mitigate | The component (Plan 04) uses the response only to render `displayName` text — no authorization decision is based on this result. Worst case (malicious Jira response) is a wrong display name shown for a cycle. Low impact. |

No high-severity threats. The new function is a thin wrapper around an existing, vetted pattern.
