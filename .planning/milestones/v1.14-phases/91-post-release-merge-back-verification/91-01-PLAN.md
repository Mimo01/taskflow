Add three exported items to `services/gitlab.ts`, placed next to their analogs.

1. `export interface GitLabCompareResult` with exactly three fields: `diffCount: number`,
   `commitCount: number`, `timedOut: boolean`. Declare it beside `GitLabBranch`/`GitLabTag`
   (around L411-423). Doc-comment it as the narrowed projection of GitLab's
   `GET /repository/compare` response, naming the three source fields it is derived from
   (`diffs`, `commits`, `compare_timeout`) and stating that `compare_same_ref` is deliberately
   NOT projected — per 91-RESEARCH Pitfall 1, `compare_same_ref` only means the two refs resolve
   to the same commit SHA, which is false in the ordinary merge-commit case (D-03) even when the
   diff is empty, so reading it as "no difference" produces false negatives.

2. `export async function compareRefs(baseUrl: string, token: string, projectId: number, from: string, to: string): Promise<GitLabCompareResult>`.
   - URL: `${base}/api/v4/projects/${projectId}/repository/compare?from=${encodeURIComponent(from)}&to=${encodeURIComponent(to)}`
     where `base` is `baseUrl.replace(/\/$/, '')`, matching every sibling fetcher.
     `encodeURIComponent` on BOTH `from` and `to` is mandatory (threat T-91-01) — release tags and
     branch names contain `/` and `.` and must never widen the query string.
   - Do NOT pass `straight` — the endpoint's default (`false`, merge-base/three-dot comparison) is
     what this phase wants.
   - Call `apiFetch('gitlab', url, { headers: { 'PRIVATE-TOKEN': token, 'Content-Type': 'application/json' } }, 'Compare Release Tag')`.
     The label `'Compare Release Tag'` must be new and distinct from every other label in the file.
     Wrap the call in `try { … } catch { throw new Error(\`Cannot reach ${baseUrl} — check the base URL\`) }`,
     verbatim in shape with `fetchBranch`.
   - Error contract, identical in shape to `fetchBranch`: on `!response.ok`, `401`/`403` throw
     `new ApiError('Failed to compare refs', response.status, 'gitlab')`; every other non-2xx throws
     `new Error(\`Failed to compare refs: status ${response.status}\`)`. Do NOT special-case 404
     into a "missing" return value — per 91-RESEARCH Assumption A1 the ref-not-found status code is
     undocumented, so the caller treats ANY thrown error as `compareCheckFailed` and degrades to
     `couldn't verify`. Never interpolate `token`, the `PRIVATE-TOKEN` header, or the full URL into
     any thrown message (threat T-91-02).
   - Parse the body as `{ diffs: unknown[]; commits: unknown[]; compare_timeout: boolean }` and return
     `{ diffCount: data.diffs.length, commitCount: data.commits.length, timedOut: data.compare_timeout }`.
     Guard the two arrays defensively (`Array.isArray(...) ? ....length : 0`) and coerce
     `compare_timeout` with `=== true`, so a malformed body degrades rather than throwing a
     TypeError inside the query.

3. `export async function fetchSourceBranchMRs(baseUrl: string, token: string, projectId: number, sourceBranch: string): Promise<GitLabMR[]>`.
   - Copy `fetchBranchTargetedMRs`'s pagination loop structurally: `const perPage = 100`,
     `let page = 1`, `const allMRs: GitLabMR[] = []`, `while (true)`, push `...data`,
     `if (data.length < perPage) break; page++;`.
   - URL: `${base}/api/v4/projects/${projectId}/merge_requests?source_branch=${encodeURIComponent(sourceBranch)}&state=all&per_page=${perPage}&page=${page}`.
     `state=all` is passed explicitly even though it is the project-scoped endpoint's default.
   - apiFetch label: `'Load Tracking MR'` (new, distinct).
   - Error contract: `401`/`403` → `new ApiError('Failed to fetch tracking MR', response.status, 'gitlab')`;
     other non-2xx → `new Error(\`Failed to fetch tracking MR: status ${response.status}\`)`.
   - DO NOT copy `fetchBranchTargetedMRs`'s label-enrichment block — the merge-back verdict never
     renders MR labels, so it would be dead code plus an extra `/labels` request.
   - DO NOT add a page cap and DO NOT fetch one page then filter client-side. This is the documented
     recurring bug class in this repo; add a comment above the loop saying so.

4. Add `merged_at?: string | null` to the existing `GitLabMR` interface (optional, so no existing
   caller or fixture breaks). Doc-comment it as: present on the MR list endpoint in practice but
   NOT confirmed by the Phase 89 live probe, therefore optional — consumers must tolerate
   `undefined` and omit the date rather than rendering an empty or invented one (planner call P-03).

Do not modify any existing function body in this file.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Taskflow renderer → GitLab REST API | Branch names and tag names derived from Jira/GitLab data are interpolated into URL query strings crossing this boundary |
| GitLab REST API → Taskflow renderer | Response bodies and error bodies are untrusted input parsed by the new fetchers |
| Taskflow renderer → devtools instrumentation | `apiFetch` records a redacted trace of every request; a raw `fetch` would bypass that redaction |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-91-01 | Tampering | `compareRefs` (`from`/`to`), `fetchSourceBranchMRs` (`source_branch`) | mitigate | `encodeURIComponent` on every interpolated ref name — a branch/tag containing `/`, `&`, or `?` must not inject extra query params or path segments. Asserted by a URL-contract test in Task 2 (`source_branch=release%2F…`) |
| T-91-02 | Information Disclosure | thrown `Error`/`ApiError` messages in both new functions | mitigate | Messages are fixed literals plus `response.status` only. `token`, the `PRIVATE-TOKEN` header value, and the full URL are never interpolated. Asserted by the 500-status test |
| T-91-03 | Information Disclosure | GitLab error response bodies | mitigate | Neither function reads or forwards the error body; the generic `status ${n}` message is used instead, so internal GitLab detail cannot reach the UI. `flattenGitLabError` is deliberately NOT wired into these read-only GETs |
| T-91-04 | Repudiation | request tracing | mitigate | Both functions call `apiFetch('gitlab', …)` with a distinct operation label (`'Compare Release Tag'`, `'Load Tracking MR'`), so every call is attributable in the redacted devtools instrumentation. A raw `fetch` would be a defect (P87 D-12a) |
| T-91-05 | Denial of Service | `fetchSourceBranchMRs` unbounded pagination loop | accept | A release branch sources at most a handful of MRs (91-RESEARCH A3); the loop terminates on any short page, and a page cap would reintroduce this repo's documented fetch-once page-cap bug class. Latency, not availability, is the residual risk |
| T-91-SC | Tampering | npm/pip/cargo installs | accept | Zero package-manager installs in this phase — 91-RESEARCH §Package Legitimacy Audit records the gate as not applicable. If a revision adds a package, the legitimacy gate must run then |
</threat_model>
