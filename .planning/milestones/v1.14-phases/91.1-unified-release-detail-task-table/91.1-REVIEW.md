## Summary

The restructure is data-layer-correct: `selectDisplayMr`'s flagged-wins/highest-iid rule is total and deterministic, the filter is applied before selection so the displayed MR always matches an active filter, the four MR-slot states kept their precedence (pending > failed > verified-empty > no-milestone, with the failed state neutral rather than orange), and `buildTaskMrAttachment`'s partition invariants are untouched.

The defects cluster in two places the consolidation created and did not re-verify:

1. **The overlay click model.** Four of six task-row cells correctly carry `pointer-events-none relative`. The two cells this task *added* — the 190px MR cell and the two 28px evaluated drift slots — do not, so ~250px of every row now swallows the D-04 full-row click, and three `title` tooltips are mounted on `pointer-events-none` elements where the browser will never render them. One of those, `mr-extra-count`, is the *only* route to the MRs the consolidation hid.
2. **Component identity vs. MR identity.** `DriftActionCell` holds per-cell mutation state but is now rendered at a fixed position whose `mr` prop can change (filter toggle, cache patch). Nothing keys it to `mr.id`, so a sticky failure — and a retry write — can land on a different MR than the one it describes.

Plus one incomplete closure of the prior CR-02: `isLoadingMilestones` was folded into `isLoadingDrift`, but the milestone query's `isError` was never destructured, so a failed milestone fetch still terminates as the settled negative "No GitLab milestone matched".

## Critical Issues (BLOCKER)

### CR-05: The consolidated MR cell and the evaluated BR/MS slots sit above the row overlay and swallow the full-row click

**Severity:** BLOCKER
**File:** `taskflow/src/routes/dashboard/release-detail/UnifiedTaskTable.tsx:471-483, 607, 633-652`

**Issue:** `TaskRow` implements the documented sibling-overlay pattern: an `absolute inset-0` button (`:687-696`) plus later siblings that either opt out of hit-testing (`pointer-events-none`) or opt above it (`relative z-10`). Both cells added by this task break the rule.

1. **The MR cell wrapper** (`:607`) is `className={`relative ${COL_MR} …`}` — positioned, *no* `z-index`, *no* `pointer-events-none`. A `position: relative; z-index: auto` element is painted in step 8 of the paint order in tree order, and it appears **after** the equally-`z-index: auto` overlay in the DOM, so it paints and hit-tests **above** it. Every pixel of the 190px MR column that is not the `!iid` link — the gap around the state badge, the badge itself (`pointer-events-none`, so the click falls to this div, not through it), the `+N` marker, all trailing whitespace — is a dead zone: clicking there calls neither `onSeedBreadcrumb` nor `onOpenIssue`. Contrast `:707`, `:710`, `:729`, which all correctly say `pointer-events-none relative`.
2. **`DriftCellSlot` is passed `interactive` unconditionally** for every evaluated MR (`:635`, `:644`), i.e. `relative z-10`, even when `DriftActionCell` renders an inert `<span>` — which it does for `mark === 'ok'` (`:254-260`), `mark === 'na'` (`:262-268`), and `mark === 'flag' && !actionable` (`:271-281`). This directly contradicts `DriftCellSlot`'s own docstring ("a purely inert cell (em-dash / check glyph) gets `pointer-events-none` instead so a click there still falls through to open the row"). The component's existing test `inert cells: ok and na marks render no button` (`:712`) proves the span case is reachable; a clean, fully-verified task therefore has two more 28px dead zones.

Net: on a typical fully-verified row roughly 250px + gaps of a ~1000px row no longer opens the issue, with no visual cue that the target moved.

**Fix:**

```tsx
// :607 — opt the wrapper out of hit-testing; the inner link already opts back in with z-10.
<div className={`pointer-events-none relative ${COL_MR} flex items-center gap-1.5 text-xs`}>

// :633-652 — derive `interactive` from whether the cell will actually be a button,
// rather than hardcoding it. Cheapest correct form: let DriftActionCell own the slot
// class, or thread the same predicate it uses:
const brInteractive = selected.br === 'flag';   // DriftActionCell renders <button> only for flag
const msInteractive = selected.ms === 'flag';
<DriftCellSlot interactive={brInteractive}> … </DriftCellSlot>
<DriftCellSlot interactive={msInteractive}> … </DriftCellSlot>
```

(The `flag && !actionable` sub-case still renders a span; `z-10` there is harmless-but-wrong — if exactness matters, hoist `configComplete && prereqReady` out of `DriftActionCell` and reuse it here.)

Add a test: `fireEvent.click(screen.getByTestId('task-row').querySelector('[data-testid="mr-cell-link"]').parentElement)` — and a click on a `drift-br` cell rendering a check — must both call `onOpenIssue`.

### CR-06: A failed GitLab-milestone fetch still terminates as the settled negative "No GitLab milestone matched"

**Severity:** BLOCKER
**File:** `taskflow/src/routes/dashboard/release-detail/useReleaseDetail.ts:138-144, 594-604` (with `UnifiedTaskTable.tsx:849-860, 568-581`)

**Issue:** The CR-02 fix added `isLoadingMilestones` to `isLoadingDrift` (`:595`) but never destructured `isError` from the `gitlab-milestones` query (`:138`), and `driftUnavailable` (`:603`) covers only channels A/B/C. When `fetchProjectMilestones` rejects — 401 after a PAT rotation, 5xx, timeout — `allProjectMilestones` is `undefined`, `isLoadingMilestones` is `false`, `isError` is discarded, so:

- `milestones` is `undefined` → `resolveGitLabMatch` returns `null` (`releaseSummaries.ts:66-68`, which cannot distinguish "no match" from "not loaded") → `hasMatchedMilestone` is `false`;
- `UnifiedTaskTable` paints the D-16 banner asserting **"No GitLab milestone matched — MR linking is unavailable."** and, when the version has no release date, adds the actively misleading remedy *"Set a release date to enable milestone matching"*;
- every task row renders `mr-slot-unavailable` with the title **"No GitLab milestone matched — cannot check for MRs"**;
- `driftUnavailable` stays `false`, so the neutral `mr-slot-failed` state built for exactly this situation is never reached.

This is the same rule `useReleaseDetail` states three times in its own comments ("A channel that cannot be queried at all is a check that did not happen, so it terminates as a FAILURE"), applied to three of four channels.

Second consequence in the same failure: `ownProjectMilestoneList` (`:401`) becomes `ownProjectMilestones([], …) === []`, and `CreateMilestoneDialog.tsx:103` runs `findDuplicateMilestone` over exactly that array — so the duplicate guard silently passes for every title and the user can create a second GitLab milestone for a release that already has one. The existing test at `useReleaseDetail.test.tsx:274` guards the *capping* regression for this array but not the failure case.

**Fix:**

```ts
const {
  data: allProjectMilestones,
  isLoading: isLoadingMilestones,
  isError: milestonesFailed,
} = useQuery({ /* … */ });

// …
const driftUnavailable = channelAFailed || channelBFailed || channelCFailed || milestonesFailed;
```

and thread `milestonesFailed` into the banner so it says "Couldn't reach GitLab to check for a milestone" instead of asserting an absence; suppress the create-milestone entry point (or its duplicate-free assurance) while `milestonesFailed` is true. Tests: a rejecting `fetchProjectMilestones` must yield `driftUnavailable === true` and must not render `drift-degraded-banner`'s "No GitLab milestone matched" copy.

### CR-07: `DriftActionCell` is not keyed to its MR, so a sticky failure — and its retry write — can bind to a different merge request

**Severity:** BLOCKER
**File:** `taskflow/src/routes/dashboard/release-detail/UnifiedTaskTable.tsx:633-652` (with `useMrFixMutation.ts:158-159, 234-240` and `UnifiedTaskTable.tsx:174-178`)

**Issue:** `useMrFixMutation` deliberately keeps `status`/`errorMessage` in **component state** so a failure survives background refetches (D-08). Before this task, each `DriftActionCell` lived on its own `MrSubLine`, keyed by `row.mr.id`, so component identity == MR identity. After consolidation, the two cells render at a **fixed position** inside `TaskMrCell` with **no `key`**, while their `mr` prop is `selectDisplayMr(mrs)` — a value that changes whenever the selection input changes. React reconciles by position, so the same hook instance is reused across MRs and its state carries over.

Reachable sequence (2-MR task, `!9` br=flag+ms=flag, `!5` br=flag):
1. No filter → `selectDisplayMr` returns `!9`. User clicks BR; the write fails; the cell is red with `!9`'s error message and is a live "click to retry" button.
2. User clicks the **"no milestone"** badge → `filteredPrimaryRows` restricts `mrs`, selection changes to `!5`.
3. The BR cell is the same instance: still red, still showing `!9`'s error text — but `fire()` now closes over `mr = !5` and issues `PUT /merge_requests/5`.

The guard at `:174-178` does not save this: `lastMarkRef` tracks only `mark`, not MR identity, so when both MRs carry `br === 'flag'` no reset fires. The equivalent bleed exists for `status === 'pending'`: a spinner and the `fire()` lock migrate onto an MR whose write was never issued. This is precisely the cross-(MR, action) leak `useMrFixMutation`'s own header calls forbidden (D-09/MRFIX-03), and the D-09 duplication tests (`:986,1003`) only cover *two separate rows*, never one row whose MR changes underneath.

**Fix:** make component identity follow MR identity.

```tsx
<DriftCellSlot interactive={…}>
  <DriftActionCell key={`br-${mr.id}`} mr={mr} action="retarget" mark={selected.br} testId="drift-br" fix={fix} />
</DriftCellSlot>
<DriftCellSlot interactive={…}>
  <DriftActionCell key={`ms-${mr.id}`} mr={mr} action="assign-milestone" mark={selected.ms} testId="drift-ms" fix={fix} />
</DriftCellSlot>
```

and widen the render-phase reset guard to reset on `mr.id` change as well as on `mark`. Test: put a task's flagged BR cell into the red state, toggle a filter that changes the selected MR, assert the cell is no longer red and that a subsequent click calls `updateMergeRequest` with the *new* iid only.

### CR-08: The `+N` marker exposes nothing — the MRs the consolidation hides are unreachable in the whole UI

**Severity:** BLOCKER
**File:** `taskflow/src/routes/dashboard/release-detail/UnifiedTaskTable.tsx:623-631` (with `:455-460`, `:775-783`)

**Issue:** `selectDisplayMr`'s contract is explicit: *"No MR is dropped from the underlying data — the rest surface behind the `+N` marker (`mr-extra-count`)."* They do not surface. The marker is:

```tsx
<span data-testid="mr-extra-count" className="pointer-events-none text-muted-foreground"
      title={`Also: ${others.map((r) => `!${r.mr.iid}`).join(', ')}`}>
```

`pointer-events: none` removes the element from hit-testing, so the browser never fires the hover that would render its `title` tooltip. The nearest ancestors carrying a `title` are none (`TaskRow`'s root has no title), so nothing is shown at all; the hit-test lands on the MR-cell div (see CR-05), which also has no title. The marker is a decoy: it announces N hidden MRs and offers no route to them.

There is no other route either. Non-selected MRs are attached to a covered task, so they are excluded from `secondaryRows` by construction (`driftDetection.ts:412-414`), and the primary table renders one MR per task. This combines badly with UAT-91.1-B: the badges are described as work queues, but `brFlaggedCount` counts *distinct flagged MRs* while the filtered table renders *one MR per task* — a task with three BR-flagged MRs contributes 3 to the badge and exactly 1 actionable row, and the other two cannot be reached, opened, or fixed from this page. The badge promises work the UI cannot deliver.

**Fix (minimum):** make the marker hit-testable so its tooltip works, and lift it above the overlay so it is not swallowed:

```tsx
<span
  data-testid="mr-extra-count"
  className="relative z-10 text-muted-foreground cursor-help"
  title={`Also: ${others.map((r) => `!${r.mr.iid}`).join(', ')}`}
>
```

**Fix (correct):** make `+N` a real affordance — a `<button>` that opens the other MRs (a popover listing `!iid` + state + BR/MS marks, each `openUrl`-able), or, at minimum, expand the task row into per-MR sub-lines on click. Without one of these, either the badge counts must switch to counting *rendered rows* rather than distinct MRs, or the "work queue" framing in `driftDetection.ts:311-338` is not honoured.

### WR-08: `+N` is computed from the filtered subset, so it under-reports while a filter is active

### WR-09: `selectDisplayMr` can surface a merged MR over a clean open one, replacing verified checks with em dashes

**Severity:** WARNING
**File:** `taskflow/src/routes/dashboard/release-detail/UnifiedTaskTable.tsx:455-460, 633-656`

**Issue:** The selection rule is flagged-first, then highest `iid` — it never considers `evaluated`. For a task with a merged MR `!42` and a clean open MR `!17`, neither is flagged, so `!42` (higher iid) wins; `selected.evaluated` is `false`, so the row falls to `naDriftCells` and renders `—` / `—` in BR and MS. The task's *actual* live MR is correctly targeted and milestoned, and the row reports "not evaluated". Pre-consolidation both sub-lines rendered and the open MR's green checks were visible. Merged MRs typically have the higher iid on a release branch that has already begun landing work, so this is the common shape late in a release cycle, not an exotic case.

**Fix:** prefer an evaluated MR when no MR is flagged:

```ts
export function selectDisplayMr(mrs: DriftRow[]): DriftRow | null {
  if (mrs.length === 0) return null;
  const flagged = mrs.filter((r) => r.br === 'flag' || r.ms === 'flag');
  const evaluated = mrs.filter((r) => r.evaluated);
  const pool = flagged.length > 0 ? flagged : evaluated.length > 0 ? evaluated : mrs;
  return pool.reduce((best, r) => (r.mr.iid > best.mr.iid ? r : best));
}
```

Update the docstring's precedence sentence and add a test for the merged-higher-iid case.

### WR-10: A partial channel failure with any MR present renders a fully confident row

**Severity:** WARNING
**File:** `taskflow/src/routes/dashboard/release-detail/UnifiedTaskTable.tsx:538` (with `useReleaseDetail.ts:603`)

**Issue:** `driftUnavailable` is a single OR across three independent channels, and `TaskMrCell` consumes it only under `mrs.length === 0`. When Channel C (branch-targeted) fails but Channel A succeeds, a task whose A-discovered MR is present renders normally with no degradation signal at all — while any MR that *only* Channel C would have found is silently missing from that task, and the `+N` count silently under-reports. The comment at `:536-537` documents the precedence but not this hole. It is the same "affirmative claim from an incomplete check" class the phase has now fixed four times, just scoped per-row instead of per-page.

**Fix:** surface the partial-failure condition page-wide rather than per-row — e.g. render a second, neutral banner ("Some GitLab merge-request lookups failed; this list may be incomplete") whenever `driftUnavailable` is true, independent of any task's `mrs.length`. Cheap, and it removes the `mrs.length === 0` coupling entirely.
