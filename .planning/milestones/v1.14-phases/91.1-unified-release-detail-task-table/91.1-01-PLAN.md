**Function 1 — `countBrMsFlaggedMRs(rows: DriftRow[]): number`** (D-15, RESEARCH A2).
Returns `rows.filter((r) => r.br === 'flag' || r.ms === 'flag').length`. Deliberately
excludes the `task` mark and does NOT read `r.flagged`. JSDoc must state why: `row.flagged`
is `br || ms || task`, and every MR uncovered by a release task carries `task === 'flag'`
by construction, so reusing `countFlaggedMRs` would inflate the badge by roughly the entire
secondary-table row count. Dedup by `mr.id` is inherent — `driftRows` is already one entry
per unique `mr.id` from `unionMRs`, so a plain `filter().length` satisfies D-15's
"distinct MRs, counted once" requirement with no extra Set. State that in the JSDoc too.
Do NOT modify `countFlaggedMRs`, `buildDriftRows`, `row.flagged`, or `buildDriftRows`'s
internal `rows.sort(...)` comparator (RESEARCH A3 — that sort becomes presentationally
inert but is locked as unchanged; leaving it is always safe).

**Function 2 — `buildTaskMrAttachment(releaseIssues: JiraIssue[], driftRows: DriftRow[])`**
(D-09, criteria 2/5). Returns
`{ primaryRows: Array<{ issue: JiraIssue; mrs: DriftRow[] }>; secondaryRows: DriftRow[] }`.
Import the `JiraIssue` type from `@/services/jira` (type-only import, matching how
`buildIssueMrIndex` already types its `releaseIssues` param in this same file).

Membership rule — **use this rule, not the one sketched in RESEARCH/PATTERNS**:

  - Build `coveredKeys = new Set(releaseIssues.map((i) => i.key))`.
  - A row is *covered* when `row.taskKeys.some((k) => coveredKeys.has(k))`.
  - `primaryRows` maps over `releaseIssues` **in Jira's returned order** (D-18 — never
    re-sort the issues), and for each issue collects
    `driftRows.filter((row) => row.taskKeys.includes(issue.key))`, sorted ascending by
    `a.mr.iid - b.mr.iid` (stable, deterministic, drift-independent sub-order per CONTEXT's
    Claude's-Discretion note). Sort a copy, never mutate the incoming `driftRows` array.
  - `secondaryRows` = rows that are NOT covered, in the incoming `driftRows` order.

**Why the rule is `taskKeys` intersection and not `taskReason !== null`** (RESEARCH and
PATTERNS both propose `taskReason !== null`; that proposal is wrong and must not be used).
`buildDriftRows` short-circuits every non-evaluated MR — merged, closed, locked
(`classifyMrState`, :236-252) — with a hardcoded `taskReason: null` regardless of its keys.
Under the `taskReason` rule such an MR is excluded from `secondaryRows`, and if none of its
`taskKeys` are in the fix version it also appears under no task — it would disappear from
the page entirely, a regression against today's `MrDriftSection`, which lists every union
row. Record this reasoning in the JSDoc so it is not "corrected" back later.

The two partitions must be **total and disjoint** over `driftRows`: every row appears under
at least one task or in `secondaryRows`, and no row appears in both. State this invariant
in the JSDoc as the function's contract.

Do not delete `buildIssueMrIndex` or `countFlaggedMRs` in this plan — plan 05 removes them
once their last consumers are gone. Keeping them here keeps the tree compiling at every wave.
