<objective>
Close the error-surfacing and dialog-hardening warnings that sit directly on the write paths the
waived live-GitLab checkpoints never exercised.

WR-11: `createBranch` and `createMilestone` short-circuit 401/403 into a generic `ApiError`
*before* reading the response body, while every other non-ok status gets the widened
`message` extraction. 403 is the single most likely failure mode for a brand-new write feature
(protected-branch rules, missing `api` scope, role restrictions) and GitLab returns an actionable
reason in the body. The dialogs render `error.message` verbatim, so today the user sees
"Failed to create branch" with no cause and no next step.

WR-01: `CreateMilestoneDialog` prefills `buildMilestoneTitle('', releaseDate)`, producing a
leading-space string like `" (21.07.2026)"`. The dialog therefore opens already invalid with the
submit button disabled and a red format error visible, and natural typing produces
`" (21.07.2026)33.5.0"`. The Jira version name is available at the call site and unused.

WR-03: only the primary button is gated on `isPending`; Cancel, Escape and the backdrop stay
live. Since inline dialog text is the only error surface (D-15 forbids toasts), dismissing
mid-flight sends a subsequent 403/500 nowhere.

Also finishes WR-10's read side: `activeGitlabProject ?? 0` at the `CreateMilestoneDialog` call
site silently empties `ownProjectMilestones`, disabling duplicate detection for every title.

Purpose: when the live-GitLab checkpoint in Plan 88-11 hits a real permission error, the user
must see why.
Output: body-first error classification, a valid prefill, modal-locked dialogs.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| GitLab response body → user-visible dialog text | Untrusted remote-controlled strings are rendered as error copy |
| Stored PAT → error strings | The token is in scope inside both write functions |
| Renderer → GitLab write API | Duplicate-detection state gates whether a POST is offered |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-88-10-01 | Information disclosure | `createBranch` / `createMilestone` error strings (WR-11) | mitigate | The thrown message is composed ONLY from `body.message` (widened for the array form) or a fixed literal fallback. The `token` parameter, the `PRIVATE-TOKEN` header and the request URL are never interpolated. Locked by Test E and by a grep acceptance criterion. `apiFetch`'s existing devtools redaction is unchanged. |
| T-88-10-02 | Tampering / XSS | GitLab `message` rendered in dialogs | mitigate | The message is rendered as a React text child of a `<p>` (auto-escaped). No `dangerouslySetInnerHTML`, no `innerHTML`, no rendering into an `href` or `src`. Verify no new sink is introduced while editing the dialogs. |
| T-88-10-03 | Elevation of privilege | Duplicate detection with project id `0` (WR-10 read side) | mitigate | The dialog now takes `number \| null` and blocks submit when unconfigured, instead of running `ownProjectMilestones` with id `0` — which filters the list empty and reports "no duplicate" for every title, allowing a colliding create attempt. Covered by Test K. |
| T-88-10-04 | Repudiation | Mid-flight dismissal swallowing write outcome (WR-03) | mitigate | Both dialogs are modal-locked while `isPending`, so a 403/500 always reaches the only error surface and a success is always acknowledged by the dialog closing itself. |
| T-88-10-05 | Denial of service | Double submit | mitigate | The primary button stays `disabled` on `isPending` and the dismissal lock removes the close-then-reopen race. Test O locks it. |
| T-88-10-SC | Tampering | npm installs | mitigate | No new dependencies. If an install appears necessary, stop and raise a blocking human checkpoint. |
</threat_model>
