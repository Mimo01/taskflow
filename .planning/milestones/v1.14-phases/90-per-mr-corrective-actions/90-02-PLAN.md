<objective>
Build the per-cell mutation layer: one `useMutation` **instance per (MR, action)**, owning an optimistic multi-cache patch with rollback and a sticky local failure state.

This is the one genuinely new architecture in the phase. Every existing `useMutation` in this codebase (`createBranchMutation`, `createMilestoneMutation`, `useFieldMutation`) is a single shared instance whose `.isPending`/`.error` describe only the most recent call — correct for one dialog, wrong for a list where several rows' BR and MS cells must be independently, simultaneously pending (**D-09**). Do not "just copy" the existing mutations; RESEARCH Pattern 3 is the authoritative worked example because no codebase precedent exists.

Two further deliberate departures: the patch uses **plural** `setQueriesData`/`getQueriesData` with the two-element `[name, projectId]` prefix (the exact windowed suffixes — `channelAUpdatedAfter`, `gitlabMatch.candidateName`, `releaseBranchName` — are unknown at the mutation site by design, and guessing them is the CR-02 bug class), and failure state lives in **component state**, not `mutation.error`, so a 5-minute-staleTime background refetch cannot wipe it (**D-08**).

Purpose: MRFIX-01/02's optimistic-with-rollback contract and MRFIX-03's independent-retry contract are both decided here; the UI plan only renders what this hook reports.
Output: `useMrFixMutation.ts` (new file, hook + three cache helpers) with a dedicated test file, plus the D-12 badge-decrement assertion in the existing `useReleaseDetail.test.tsx`.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| UI intent -> write payload | The only place the app decides *what* gets written to a merge request |
| GitLab error -> component state | Server-controlled text is stored and later rendered in a tooltip (D-07) |
| Query cache -> rendered drift state | An optimistic patch temporarily makes the UI disagree with the server |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-90-06 | Tampering | `useMrFixMutation.mutationFn` | mitigate | The write target is never free-form: `target_branch` can only be the hook's `targetBranch` argument (the release branch resolved by `useReleaseDetail`) and `milestone_id` only `milestone.id` (the date-matched release milestone). No user-typed string reaches either field; ASVS V5 is satisfied by construction, not by validation. Asserted by tests that inspect the `updateMergeRequest` call arguments. |
| T-90-07 | Tampering | write against an unresolved target | mitigate | WR-10 guards throw before the service call when `projectId`/`baseUrl`/`token`/`mr.iid`/`targetBranch`/`milestone` is falsy; `?? 0` and `?? -1` are grep-forbidden by this plan's acceptance criteria. The optimistic patch is likewise gated on a non-null `projectId` so cache writes cannot be attributed to project `0`. |
| T-90-08 | Information Disclosure | `errorMessage` in component state | mitigate | Stores only `Error.message` produced by Plan 01's `updateMergeRequest`, which composes messages solely from `flattenGitLabError(body)` or a fixed literal — no URL, header, or token. The hook never stringifies the `Response` or the request options. |
| T-90-09 | Repudiation | silent partial failure | mitigate | Rollback restores every touched cache entry by its own exact key, and the failure is sticky (D-08) rather than transient, so a failed write cannot be mistaken for a successful one after a background refetch. |
| T-90-10 | Denial of Service | double-fire / retry storm | mitigate | Per-cell lock: `fire()` returns early while `status === 'pending'`, so a double-click cannot issue a second PUT; retries are user-initiated only, with no timer and no automatic backoff loop. |
| T-90-SC | Tampering | npm/pip/cargo installs | mitigate | No new dependencies (RESEARCH: audit not applicable). An executor reaching for `npm install` must stop; `[ASSUMED]`/`[SUS]` packages would require slopcheck plus a blocking human checkpoint. |
</threat_model>
