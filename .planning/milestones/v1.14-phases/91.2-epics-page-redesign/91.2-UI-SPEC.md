# Phase 91.2 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | shadcn (already initialized — `taskflow/components.json`) |
| Preset | `base-nova` (baseColor: neutral, cssVariables: true, no class prefix) |
| Component library | base-ui (`@base-ui/react/*` primitives, e.g. `Progress`) |
| Icon library | lucide-react |
| Font | `Geist Variable` (`--font-sans`, `src/index.css:50`) |

This phase does not initialize anything new — it reuses the app's existing token set and component vocabulary (`statusPillClass`, `epicColorToTailwind`, `PriorityIcon`, `CachedAvatar`, `Progress`/`ProgressTrack`/`ProgressIndicator` base-ui wrapper, `EmptyState`/`ErrorState`/`StaleDataBanner`, `Skeleton`). No new shadcn blocks are pulled in. Registry safety gate: not applicable (no new registry usage).

## Visual Focal Point

The row's primary visual anchor is the three-segment progress bar — it is the largest, most colour-saturated element in the row and should draw the eye first (scanning a list of 20-30 epics, "how done is this" is the dominant question). The epic-colour treatment (D-09) is a secondary identity cue, not a competing focal point — per the Component Contract below, it must be scaled back (single carrier, not double-encoded) so it doesn't out-compete the progress bar for attention.

## Spacing Scale

Declared values (must be multiples of 4), matching the app-wide density system (`data-density="compact|default|comfortable"`, `@variant density-compact`/`density-comfortable` in `src/index.css`):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon gaps, segmented-bar internal gaps |
| sm | 8px | Compact-density cell vertical padding (`density-compact:py-1.5` ≈ 6px, rounded to the 4px grid via existing Tailwind step) |
| md | 16px | Default-density cell padding (`px-4`), inter-cell gaps |
| lg | 24px | Page header padding (`px-6 py-4`, existing, unchanged) |
| xl | 32px | Not used on this page |
| 2xl | 48px | Not used on this page |
| 3xl | 64px | Not used on this page |

Exceptions:
- Row height is density-driven per D-07 (one line at every density) — compact/default/comfortable each set a fixed min-height via the existing `density-compact:py-*` / `density-comfortable:py-*` Tailwind variants already present in `EpicRow`. No new density tier is introduced.
- The 1px epic-colour bar column (`<td className="w-1 p-0">`) is a deliberate sub-4px exception, carried over unchanged from the current implementation.

## Typography

Reuses the app's existing type scale (no new sizes introduced). Declared for this phase's cells — exactly 2 weights, no exceptions:

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body (table cell default — key, epic name badge, points, assignee name) | 14px (`text-sm`) / 12px (`text-xs`) for the epic key mono and badge text | 400 regular | 1.5 |
| Label (done/total counts, `SP` unit, hover breakdown) | 12px (`text-xs`) | 400 regular | 1.5 |
| Heading (page title "Epics") | 20px (`text-xl`) | 600 semibold | 1.2 |

The epic-name badge drops its previous `font-medium` (500) to `font-normal` (400) as part of this redesign — emphasis for the badge is carried by its color tint/border (`epicColorToTailwind`) and the D-09 colour treatment, not by font weight, so a third weight is unnecessary. This is a deliberate, minor visual simplification (not an "inherited exception") made to satisfy the 2-weight limit while keeping the badge legible.

## Color

The row keeps the app's existing 60/30/10 background system unchanged (page background, table row hover `bg-muted/30`, borders `border-border`). This phase's new visual surface is the three-segment progress bar and the epic-colour treatment (D-09, Claude's discretion).

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `bg-background` (existing token) | Page background, table row background |
| Secondary (30%) | `bg-muted` / `bg-muted/30` (existing tokens) | Row hover, progress-bar track background, skeleton shimmer base |
| Accent (10%) | Status-category tones, reused from `statusStyles.ts` — `bg-green-500` (done), `bg-blue-500` (in progress), `bg-gray-400`/`bg-muted` (to do) | **Reserved exclusively for: the three segments of the progress bar, and the existing status pill / epic-colour badge.** Not used for any other row chrome. |
| Destructive | `text-red-600 dark:text-red-400` / `bg-red-500/15` (existing `CHIP_TONE_CLASS.red`) | Reserved for the D-15 enrichment-failure warning glyph only (muted ⚠, click-to-retry) — no other destructive/error color use on this page |

Accent reserved for: the Done/In-Progress/To-Do segments of the new three-segment progress bar (derived from `statusCategoryDotClass`/`statusCategoryBadgeClass` tokens — green/blue/gray-muted, per D-09 discretion note "derive from the existing status-category token vocabulary, not a new palette"), the existing status pill, and the epic-colour identity bar/badge (D-09 redesign — see Component Contract below). No accent color is introduced for hover affordances, buttons, or generic chrome beyond what already exists on the page (the "+ Create Epic" button keeps its current neutral `border-border`/`bg-background` styling — unchanged).

## Component Contract (phase-specific — supplements the template)

This section captures the concrete row/column contract locked by `91.2-CONTEXT.md`, since the standard template sections above under-specify a redesign this data-dense.

**Column order (left→right):** epic key · epic name · status · priority · progress (segmented bar + `done/total`) · story points (`done/total SP`) · assignee. (D-05, D-06 — key now precedes name, reversed from today.)

**Row shape:** exactly one line per epic at every density tier (compact/default/comfortable) — no wrapping, no stacked second line (D-07). Density changes padding/font-size only, never row structure.

**Labels/components:** not rendered on this page at all (D-08 — descopes ROADMAP criterion 4's labels half). Remain visible only in `EpicDetailSheet`.

**Epic-colour treatment (D-09, Claude's discretion at implementation time):** today's double encoding (1px left colour bar + colour-badge epic name) may be kept, reduced, or redesigned — constraint is that epic colour identity must stay legible (shared visual language with Backlog filter chips and Sprint Board epic swatches) and must not visually compete with the new segmented progress bar. Executor should pick ONE primary colour carrier (bar OR badge tint, not necessarily both at full strength) to keep the row calm.

**Priority column:** `PriorityIcon` only (icon + `title`/alt text carrying the priority name) — no visible priority label text in the row (D-10).

**Progress + child-status breakdown — ONE visual, not two:**
- A single three-segment horizontal bar: Done (green, `statusCategoryDotClass('done')` → `bg-green-500` family) / In Progress (blue, `bg-blue-500` family) / To Do (gray, `bg-gray-400`/muted family) — ordered done→in-progress→to-do, matching the row sketch in CONTEXT.md.
- `done/total` count (e.g. `8/12`) sits beside the bar (inline placement is Claude's discretion — sketch shows inline right of bar).
- Per-status counts revealed on hover only (native `title` attribute is the safe default — CONTEXT.md notes no tooltip primitive exists in `components/ui/`; do not introduce one for this phase).
- **No blocked/flagged segment, marker, or count anywhere** (D-12 — descopes ROADMAP criterion 5's blocked/flagged half). The Jira Flagged field (`flaggedFieldKey`) must never be fetched by this page's enrichment query.

**Story points:** `done/total SP` (e.g. `21/34 SP`), not a single total (D-13). Requires new `donePoints` aggregate in `fetchEpicEnrichmentMap`.

**Enrichment cell states (progress cell + points cell only — rest of row renders fully at first paint from `fetchEpicsBasic`):**
1. **Loading (D-14):** skeleton shimmer matching `EpicsSkeleton`/issue-detail skeleton convention, sized to the settled column width (no reflow when data lands).
2. **Success, has stories:** segmented bar + `done/total` / `done/total SP` as specified above.
3. **Success, zero stories (D-16):** muted "No stories" text, no bar — visually distinct from both other states.
4. **Failure (D-15):** inline muted ⚠ + click-to-retry, re-firing just that epic's enrichment lookup. `fetchEpicEnrichmentMap` must stop swallowing errors to `.catch(() => [])` — the failure must reach the component as a real error state (same fail-closed correction class as `searchProjectTags` in Phase 91-07).

**Ordering:** `ORDER BY created ASC` (creation-ascending, equivalent to key order) replaces today's `updated DESC` in `fetchEpicsBasic`. **Fixed — not click-sortable.** No column headers should imply sortability (no sort-arrow affordance, no `cursor-pointer` on header cells for this reason). Enrichment merging into existing rows must never reorder them.

**Search:** explicitly CUT (D-18). No search input, no `/` keybinding, no filter predicate, no result count, no distinct no-match empty state. Page header keeps exactly its current shape: "Epics" title left, "+ Create Epic" right.

**Row click / hit-testing:** `onEpicClick` → `EpicDetailSheet` must remain unchanged and fire from anywhere in the row except the D-15 retry glyph's actual click target. Per the 91.1 CR-05 precedent (an inner cell swallowed row clicks across ~190px of every row), the retry affordance must be a small, precisely-bounded interactive element — not a full-cell overlay — so it doesn't silently eat row-click area. Verify hit-testing manually, not just visually.

**WebKit zero-width column guard (ROADMAP criterion 8):** every column must carry an explicit width (px or a Tailwind fixed-width class), mirroring the `CachedAvatar`-style fix already used elsewhere in this codebase. The current `<colgroup>` (`w-1`/`w-16`/`w-28`) is the shape at risk when new columns (priority, progress, points) are added — verify in the real Tauri/WebKit webview at all three densities, not only in jsdom/Vitest.
