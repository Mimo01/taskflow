# Phase 91.2: Epics Page Redesign - Context

**Gathered:** 2026-08-12
**Status:** Ready for planning

<domain>
## Phase Boundary

`/epics` stops being a five-column name/key/status/assignee list and becomes a useful epic-portfolio surface: epics ordered by creation (oldest-first / key order), with each row carrying story progress, story points, priority, and a child-status breakdown — without regressing the deliberate fast-first-paint behaviour the page has today.

**The quick-search box is cut** (D-18) — it was discussed, settled, then reversed by the user. ROADMAP criterion 2 is descoped in full.

Scope is `src/routes/dashboard/EpicsPage.tsx` + `EpicsSkeleton.tsx` + the two epic fetchers in `src/services/jira/epics.ts`. `EpicDetailSheet` behaviour on row click is unchanged. This is not an epic-management feature phase — no new write actions beyond the existing "+ Create Epic".

</domain>

<decisions>
## Implementation Decisions

Roadmap-time decisions D-01…D-04 (layout = table not cards, no aggregate summary strip; extra data = progress/points/priority/labels/child-breakdown; Done epics stay hidden with no toggle; enrichment must not block first paint) remain in force and are not restated below except where this discussion narrowed them.

### Row shape and columns

- **D-05:** Column order is **key first**, then epic name — reversed from today's name-then-key. Explicit user instruction.
- **D-06:** Final column set (left→right): epic key · epic name · status · priority · progress (segmented bar + `done/total`) · story points · assignee. Plus whatever colour treatment D-09 lands on.
- **D-07:** **One epic = one line at every density** (compact, default, comfortable). Explicit user instruction — no stacked second line, no wrapping cell, at any density. Density changes padding/font only.
- **D-08: Labels and components are NOT shown on the list page at all.** User: *"I dont need labels at all on the list page."* This **descopes the "labels/components" half of ROADMAP success criterion 4** — priority is still required, labels/components are not. Handle as an intentional descope (same class as DASH-06 in P84 and DRIFT-09 in P89), not a gap. Labels remain available in `EpicDetailSheet`.
- **D-09:** The epic-colour treatment is **Claude's discretion** — today's double encoding (1px left colour bar *and* the name rendered as a coloured badge) may be kept, reduced, or redesigned. User: *"Redesign it, i leave it up to you. make sure it looks good and modern."* Constraint: epics must still read as epics (colour identity is used across backlog filter / sprint board), and the row must not become visually noisy alongside the new segmented bar.
- **D-10:** Priority renders via the existing `PriorityIcon` (the real Jira `iconUrl` for the project's 9-level scheme) — icon only, name in `title`/alt.

### Progress and child-status breakdown

- **D-11:** Progress and the child-status breakdown are **one visual, not two columns**: a single **three-segment bar** (Done / In Progress / To Do, by Jira **status category**) with `done/total` (e.g. `8/12`) beside it, and the per-status counts revealed on hover.
- **D-12: No blocked/flagged segment, marker, or count anywhere on the list page.** The user first chose a fourth blocked segment, then reversed it: *"Flags are ignored, flag is just a flag, not a progress marker. only statuses count"*, and then selected three categories only. Net effect: the Jira **Flagged field is never fetched and never read** by this page (`flaggedFieldKey` from `services/jira/fields.ts` is not needed), and no blocked-status segment is split out either. This **descopes the "plus a count of blocked/flagged children" half of ROADMAP success criterion 5** — the To Do / In Progress / Done breakdown itself is still required. Intentional descope, not a gap.
- **D-13:** Story points render as **`done/total` points** (e.g. `21/34 SP`) — not a single total. This requires a new `donePoints` aggregate in `fetchEpicEnrichmentMap` alongside the existing `{total, done, points}`.

### Enrichment streaming and failure

- **D-14:** While the enrichment query is in flight, the progress cell and the points cell render **skeleton shimmer** (consistent with `EpicsSkeleton` and the per-section issue-detail skeletons), swapping in place when data lands. The rest of the row is fully rendered from `fetchEpicsBasic` at first paint.
- **D-15:** On enrichment **failure**, those cells show an **inline muted warning glyph with a click-to-retry** — not zeros, not silence. This means `fetchEpicEnrichmentMap` **must stop swallowing errors to an empty result** (it currently ends in `.catch(() => [])`); the failure has to reach the component as a real error state. Same fail-closed correction as `searchProjectTags` in Phase 91 (91-07) and the same absence-of-evidence class of bug as 88-CR-01 / 91.1-CR-06.
- **D-16:** An epic that genuinely has **zero child stories** (successful enrichment, empty result) shows muted **"No stories"** text and no bar — visually distinct from both the loading shimmer (D-14) and the failure marker (D-15).

### Ordering and sorting

- **D-17:** Epics are ordered **creation-ascending** (`ORDER BY created ASC`, equivalent to key order), replacing today's `ORDER BY updated DESC` in `fetchEpicsBasic`. This ordering is **fixed — the columns are not click-sortable**. The table borrows the Backlog/Releases *visual* idiom only. This directly protects criterion 1's "the order never re-shuffles while enrichment data streams in": enrichment merges into existing rows and can never reorder them.

### Quick search — CUT

- **D-18: There is no search box on the Epics page.** The quick-search feature was discussed in full and settled (header placement, `/` shortcut, name/key/summary substring matching, reset-on-leave, `12 of 30` count, dedicated no-match state) and then **reversed by the user**: *"I have changed my mind, I dont want any new search bar added to the epics page."*

  This **descopes ROADMAP success criterion 2 in its entirety** — no input, no `/` binding, no client-side filter predicate, no result count, no no-match empty state. The existing "No epics yet" `EmptyState` remains the page's only empty state and needs no distinct sibling. Intentional descope by explicit user decision (same handling class as DASH-06 in P84, DRIFT-09 in P89, MERGE-03 in P91) — its absence is **not** a gap at verification time.

  The page header therefore keeps its current shape: "Epics" title on the left, "+ Create Epic" on the right.

### Claude's Discretion

- The epic-colour visual treatment (D-09) — full redesign latitude, must look modern and keep epic identity legible.
- Exact segment colours for the three-category bar — should derive from the existing status-category token vocabulary (`statusPillClass` colours) rather than introduce a new palette.
- Bar height, corner treatment, and whether the `8/12` sits inline or below.
- Hover-reveal mechanism for the per-status counts (native `title` vs a popover) — note the app has no tooltip primitive in `components/ui/`.
- Skeleton geometry for the two shimmering cells, as long as it matches the settled row's column widths (no reflow on data arrival).

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `fetchEpicsBasic` / `fetchEpicEnrichmentMap` both already exist in `services/jira/epics.ts`; the enrichment fetcher is currently **dead code from this page's perspective** (nothing calls it here). The phase wires it in progressively rather than writing a new fetcher.
- `PriorityIcon`, `statusPillClass`, `CachedAvatar`, `epicColorToTailwind`, `useDelayedLoading`, `EmptyState` / `ErrorState` / `StaleDataBanner` all already do their jobs on this page or an adjacent one — the redesign should be additive over them, not a fresh component vocabulary.

### Established Patterns
- **Progressive enrichment behind a fast basic query** is the house pattern (sprint board subtasks, backlog epic metadata — v1.7). Enrichment is a *second* `useQuery` keyed off the loaded epic keys, merged at render; it must not gate the first query's render.
- **Fail-closed over fail-silent.** Three separate phases (88, 91, 91.1) shipped blockers where a swallowed error rendered as verified-negative data. D-15 exists to avoid repeating that here.
- **Narrow columns collapse to zero width in the Tauri/WebKit webview** — a recurring bug in this codebase (fixed previously with explicit-px sizing, e.g. `CachedAvatar`). ROADMAP criterion 8 exists for exactly this; the current `<colgroup>` with `w-1` / `w-16` classes is the shape at risk. Verify at all three densities in the real webview, not just jsdom.
- **`statusPillClass` needs a flex wrapper** — a bare `<span>` in a `<td>` collapses its `min-w`/`text-center`.
- **Test suite convention:** Vitest with the LazyStore mock; component tests colocated.

### Integration Points
- `onEpicClick` arrives via `useOutletContext` and opens `EpicDetailSheet` — **unchanged** (criterion 7). Any new interactive element inside the row (the retry affordance in D-15, the hover target in D-11) must not steal the row click — see the 91.1 CR-05 precedent, where an inner cell swallowed row clicks across ~190px of every row.
- `CreateEpicDialog`, the "+ Create Epic" button, and the page header stay exactly as they are (D-18 cut the only planned header change).
- Query key `['jira-epics-basic', activeJiraProject, jiraBaseUrl]` is shared — check for other consumers before changing its shape. The new enrichment query needs its own key.
- PROJECT.md's Key Decisions table still records *"EpicsPage uses fetchEpicsBasic (not fetchEpicsWithEnrichment) — enrichment too slow for list view"*. That decision is **superseded** by roadmap D-04 (enrichment accepted, progressively, behind first paint). Worth updating that row at milestone close.
