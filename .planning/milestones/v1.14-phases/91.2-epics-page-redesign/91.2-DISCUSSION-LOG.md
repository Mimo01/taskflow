# Phase 91.2: Epics Page Redesign - Discussion Log

> **Audit trail only.** Do not use as input to planning, research, or execution agents.
> Decisions are captured in CONTEXT.md — this log preserves the alternatives considered.

**Date:** 2026-08-12
**Phase:** 91.2-epics-page-redesign
**Areas discussed:** Column set & row shape, Progress & child-status breakdown, Enrichment streaming & failure, Quick-search behaviour (later cut), Sorting, Points semantics

---

## Column set & row shape

| Option | Description | Selected |
|--------|-------------|----------|
| 8 columns, labels in name cell | Label chips stacked under the epic name so they need no column width; densest layout keeping everything visible | ✓ (later superseded) |
| 9 flat columns, labels own column | Every data point its own column including labels with +N; closest to Backlog/Releases idiom, but narrowest columns are exactly the WebKit zero-width risk | |
| Merge status into breakdown | Drop the epic's own status column and let the child breakdown carry the information | |

**User's choice:** 8 columns with stacked labels — then superseded twice by direct instruction.
**Notes:** Follow-up question on compact density → "Labels inline after name". Then, asked how many label chips before a +N, the user answered *"I dont need labels at all on the list page"* and separately sent *"every density must have one epic on one line"* and *"the key must be first in the epic row"*. Net result: no labels/components at all, one line at every density, key-first column order. ROADMAP criterion 4's labels/components half is descoped.

## Blocked / flagged children

| Option | Description | Selected |
|--------|-------------|----------|
| Warning marker beside the bar | Amber flag + count only when > 0; quiet on healthy epics | |
| Fourth segment in the bar | Blocked as its own bar segment; flagged noted as orthogonal to status | ✓ (then reversed) |
| Row-level warning tint | Amber row edge, no magnitude | |

**User's choice:** Fourth segment — then reversed.
**Notes:** Asked to settle the double-count rule and what "blocked" means (flagged field vs status name containing "block"), the user answered *"Flags are ignored, flag is just a flag, not a progress marker. only statuses count"*. A clarifying question then offered: blocked-status as the 4th segment / three categories only / one segment per actual status. User chose **three categories only**. Net: no blocked signal on the list page at all, Flagged field never fetched. ROADMAP criterion 5's blocked/flagged-count half is descoped.

## Claude's Discretion

- Epic-colour visual treatment — full redesign latitude ("looks good and modern"), epics must still read as epics.
- Segment colours for the three-category bar (should derive from the existing status-category token vocabulary).
- Bar height, corner treatment, `8/12` placement.
- Hover-reveal mechanism for per-status counts (no tooltip primitive exists in `components/ui/`).
- Skeleton geometry for the two shimmering cells (must match settled column widths — no reflow).

## Deferred Ideas

- Click-to-sort columns — considered and rejected; creation order is fixed.
- Quick search / any filtering on the epics list — fully specified, then cut. Design recoverable from this log.
- Labels and components on the list row — cut; remain on `EpicDetailSheet`.
- Any blocked/flagged surfacing on the epics list — cut; would be its own decision, not a re-open.
- Aggregate header summary strip — already rejected at insert time (roadmap D-01), reconfirmed here.
