**Root cause analysis (do not re-research — apply directly):**

1. `jiraDefectIDs` from AIO are numeric internal Jira IDs (`number[]`, e.g. `[186227]`). See `taskflow/src/services/aio/cycles.ts:406` (`item.latestTestRun?.allDefects`) and `taskflow/src/services/aio/issue-runs.ts:46-60`. The string `'186227'` is currently treated as the defect key throughout DefectRow (rendered, linked, used as fetch input).
2. Jira's `/rest/api/2/issue/{idOrKey}` endpoint accepts BOTH numeric IDs and keys, so `fetchJiraIssueByKey(numericId)` succeeds and returns the issue with the canonical `.key` field populated. Therefore: keep the existing fetch input as-is, but RENDER `issueQuery.data?.key` (with `defectIdOrKey` as fallback while loading), and link to `/issue/${issueQuery.data?.key ?? defectIdOrKey}`.
3. The current status pill uses `bg-muted text-muted-foreground` hard-coded — no statusCategory lookup. Replace with `statusPillClass(issueQuery.data?.fields.status.statusCategory?.key)` and render `issueQuery.data?.fields.status.name` inside it (matching how `IssueDetailContent.tsx:158` and `TaskCard.tsx:142` do it).
4. Assignee is not rendered at all in DefectRow — but the Jira issue we already fetch contains `fields.assignee.displayName` and `fields.assignee.avatarUrls['48x48']`. No extra query needed; reuse `CachedAvatar` (already imported).
