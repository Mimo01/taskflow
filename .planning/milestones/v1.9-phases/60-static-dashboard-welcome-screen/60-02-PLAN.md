<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| React state → Jira REST API | `jiraToken` prop is sent in `Authorization` header by `fetchSprintIssues` |
| Jira API response → React render | Issue summaries, keys, and assignee displayNames traverse from external API into JSX |
| User click → router | `navigate(`/issue/${key}`)` interpolates `issue.key` into a URL path |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-60-04 | Information Disclosure | `jiraToken` prop | mitigate | Token never rendered to DOM; passed only to `fetchSprintIssues` for Authorization header (T-60-01 from plan 01 applies symmetrically) |
| T-60-05 | Tampering (XSS) | issue.fields.summary, issue.key rendered as text | mitigate | React JSX auto-escapes; no `dangerouslySetInnerHTML`; no `innerHTML` writes |
| T-60-06 | Tampering (open-redirect) | `navigate(\`/issue/${issue.key}\`)` uses a Jira-provided key | mitigate | `useNavigate` resolves a relative path against the SPA router; never a full URL; `/issue/:key` is a known internal route — Jira issue keys are `[A-Z]+-\\d+` and cannot escape the route shape |
| T-60-07 | Information Disclosure | Filter exposes another user's subtasks if `jiraUserDisplayName` is empty (every assignee?.displayName === '' check fails — but `null === ''` is false in TS, so filter returns no rows) | accept | The filter correctly returns 0 rows when `jiraUserDisplayName === ''` (empty state shows); confirmed by Task 1 Test 4 |
</threat_model>
