<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| User input → tempo-filters store | Free-text filter names typed by the user enter the store and are persisted to disk. |
| Saved filter load → WorklogsPage state | Stored preset/username values are read and re-applied to React state and Jira API queries on the next render. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-63-04 | Tampering | Filter-name input on WorklogsPage | accept | The name field is for the local user only; it is never sent to any external service. Whatever the user types is what they get back. React's default JSX escaping handles render-time XSS naturally. |
| T-63-05 | Information Disclosure | Filter pill label rendering | accept | Filter names are user-authored and rendered via standard JSX text interpolation (React escapes by default). No `dangerouslySetInnerHTML` is used in this phase. |
| T-63-06 | Tampering | Saved-filter `preset` and `username` values applied to Jira API query | mitigate | The `preset` field is type-narrowed to `DatePreset` (string union) by TypeScript; `username` is a string and is interpolated into existing Jira queries that already accept it as a parameter (Phase 62 already validated this path). No new injection surface is introduced. |
| T-63-07 | Denial of Service | Unbounded saved-filter list slowing render | accept | The list renders as a flex-wrap row; render cost is O(n) and bounded by what a user is willing to type. Same risk profile as the existing pinned tabs list. |
| T-63-SC | Tampering | npm package installs | mitigate | No new packages installed in this phase. |
</threat_model>
